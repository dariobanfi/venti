# Notes for AI sessions working on the Android app

Working notes: what to know before changing the app or its tests. What the app does and what is not built is in [docs/plan.md](../../docs/plan.md) and [docs/design.md](../../docs/design.md), how it is built and what is still to verify on a phone in [docs/architecture.md](../../docs/architecture.md#android). The `README.md` beside this file is for people.

## Setting up and installing

- **What a build needs**: Java 17 or later; Rust from rustup with `rustup target add aarch64-linux-android x86_64-linux-android`; `cargo install cargo-ndk --version 4.1.2 --locked`; the Android SDK with platform 37, build tools 36.0.0 and NDK 29.0.14206865. Android Studio installs them when it opens the project; without it, `sdkmanager "platforms;android-37.0" "build-tools;36.0.0" "ndk;29.0.14206865"`, with `ANDROID_HOME` (or `sdk.dir` in `apps/android/local.properties`) pointing at the SDK. Keep the SDK out of the repository.
- **The tasks**, from `apps/android`: `./gradlew :app:assembleDebug` writes `app/build/outputs/apk/debug/app-debug.apk`, `:app:installDebug` puts it on a connected phone or a running emulator, `:app:connectedDebugAndroidTest` runs the UI tests there.
- **Installing without building.** Every push that touches the app builds a debug copy, the `venti-debug-apk` artifact of the `Android` workflow: `gh run download --name venti-debug-apk --dir /tmp/venti`, then `adb install -r /tmp/venti/app-debug.apk`. It runs on 64-bit phones with Android 8 or later. Each build machine signs with a throwaway key of its own, so a build from another machine does not install over it: remove the app first, and its logbook with it.

## Checks before a push

- **When the owner's Mac is attached to the session, run the UI tests on its emulators with `scripts/ui-tests.sh`, not through CI.**
  - `scripts/ui-tests.sh` runs them all on 3 emulators; `scripts/ui-tests.sh theCockpitWarnsOfAirspace theMapNamesPlaces` only those (a function of `VentiUiTest`, or `Class#function`, or a class); `-n 4` on four, `--no-build` with the last build, `--stop` stops the emulators at the end. It needs `target/debug/venti-server` built, and runs with the sandbox off.
  - It builds once while the emulators start, installs on each by its serial, gives each emulator its own fresh pair of servers (8190/8191, 8192/8193, …), and has the emulators take the tests from one queue, the longest first as the last run timed them (`target/android/ui-tests/timings.txt`). Each test runs in an instrumentation of its own (`adb shell am instrument`, not Gradle's `connected…` task, which cannot give two devices different servers). Everything lands in `target/android/ui-tests/<run>/`: `screenshots/` with every test's pictures, a log for each test, and one line for each test at the end.
  - The emulators are the virtual devices `pixel6-api36-b`, `-c`, `-d`, `-e` on the ports 5556, 5558, 5560, 5562; the script makes those missing as copies of `-b` and leaves them running for the next run, which then starts at once. `emulator-5554` (`pixel6-api36`) is the owner's windowed one: the script never touches it, and neither does a session.
  - By hand, for one test through Gradle: the SDK is Homebrew's (`ANDROID_HOME=/opt/homebrew/share/android-commandlinetools`), Java `openjdk@21` (`JAVA_HOME=/opt/homebrew/opt/openjdk@21`, its `bin` on the path), rustup's tools before Homebrew's `cargo`; **`ANDROID_SERIAL=emulator-<port>` exported before every `connected…` or `install…` task**, or Gradle installs on every emulator that runs and its uninstall kills what another session or the owner has open there; then `./gradlew :app:connectedDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.ventiServer=http://10.0.2.2:8190 -Pandroid.testInstrumentationRunnerArguments.madeUpDayServer=http://10.0.2.2:8191 -Pandroid.testInstrumentationRunnerArguments.class=fly.venti.app.VentiUiTest#<name>`, against a fresh `venti-server dev` and made-up day on those ports, stopped at the end.
- **What the UI tests taught on 2026-11-21.** A row that is one element for TalkBack (`clearAndSetSemantics` with a description) has no text of its own: find it with `described("…")`, not `hasText`. A page that is a lazy list holds a row only while it is scrolled into view, and comes back at its head from a screen opened over it: scroll to a row (`performScrollToNode`) before waiting for it, each time. A chip beyond the edge of its row is not tapped by a tap: `tapChip` scrolls the row to it first. Each of these passed on screen and failed in the test, and each cost a CI round before the tests ran on the owner's Mac.
- From `apps/android`, with `ANDROID_HOME` set: `./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebugAndroidTest -Pventi.abis=x86_64`. The unit tests call the real core; the last task only compiles the UI tests.
- Run them again after every rebase that brings a change to `crates/core`. A field added to a record of the core breaks the tests that build that record by hand: `ReachTest` (`ReachView`), `AheadTest` (`AirspaceAheadSpan`), `WindByHeightTest` (`WindAtHeightView`), `GroupsModelTest` (`GroupMember`). Where a test needs a changed record, take a real one from the core and use `copy`.
- Lint fails on a drawable that nothing uses: add an icon in the commit that uses it.
- The UI tests cannot run in a cloud session. The `Android` workflow runs them, in about half an hour. A run that has started finishes; of the runs waiting behind it only the newest is kept, so a push is often tested together with later commits.
- When a run is red: the artifact `android-test-reports` holds `TEST-*.xml` with the failed test and the line, and `android-screenshots` holds `failed-<test>.png`. That picture is the last frame that was drawn, which can be older than what the failed assertion looked at.

## Pitfalls of the UI tests

- A made-up flight must come down to the ground the app knows (`LiveFlightTest`): the core does not end a flight while the terrain lies more than 50 m below (it waits five minutes there), and the emulator's barometer holds the height of the first fix, so a height fed later does not bring the glider down. `aFlightRecordsItself` flies at the take-off's ground and lands where it started, and flies one full circle on the way (36 s): since 2026-11-22 a flight that has shown nothing only a glider does is taken back by the core when it comes to rest. A position fed through the emulator's console (`adb emu geo fix … <speed>`) is held with its speed after the feeding stops, and the take-off watch then sees a take-off in the next test: end with a fix of speed 0.
- The words of the controls every screen has (Done, Back, More, OK, Cancel, Try again, Close) are the core's, `Common.words` (`design/Common.kt`); write no copy of them.
- A replay goes on while a test looks, by two seconds of the clock at most for each refresh. What belongs together during a thermal or a glide is looked for at one look (`waitForAll`); what comes late in a flight is waited for with `TestDevice.WHOLE_FLIGHT_SECONDS`.
- A screenshot waits until the map has drawn all it was given (`TestDevice.keepScreenshot`, `letTheMapFinish`). The glider and its track are one large piece of data and reach the map later than the line to the target does.
- Rows that are one element for a screen reader end their modifiers with `clearAndSetSemantics`: a test tag before it stays, tags on what is inside the row are gone. Find such a row by its tag, its description and what it says (`saying`).
- An instrument is read as "1,453 m, 238 m over ground": the value, then the line under it. A test that takes a number from it takes the first.
- Words on screen are mostly the core's. Read them in `crates/core` before asserting them: in a plan's list of who is in, the pilot of the phone is "You"; a place out of reach says "Out of reach." or "Out of reach: the ground is in the way."
- `venti-server dev` keeps what the tests send until it stops, and the light and the dark test run against the same one. A second report about the same thing is not a new one, so the two appearances report two pilots' flights; both post a plan for today. Its demo pilot signs in as `demo` with `demo-pilot-password`; neither is a secret.
- A bottom sheet stops at half height only if its content is taller than half the screen when it opens: wrap the content in `Box(Modifier.fillMaxHeight())`.
- A sheet whose content comes to about the screen's height, pulled up to its end, kept Compose recomposing and the app drawing ten frames a second without end, and a test then fails with "Compose busy … pending recompositions" (`MapLayersSheet` with the development server's rows, 2026-11-23; Material 3 1.4.0). Its content now fills the height (`fillMaxHeight()` on the scrolling column). Whether the same happens on a phone outside a test is to verify; a sheet of many rows that scrolls far is not affected.
- With a sheet open over a sheet there are two "Done" buttons: give the upper one a test tag (`report-close`).
- What explains stands behind a row since 2026-11-22 (the owner: default screens stay simple). A site's page keeps its notes on the layers and the wind near by, the caution, the source's notice and credit behind "How this is read" (`site-how-read`, the last row; `unfoldHowASiteIsRead()` in the tests); a station's page keeps the air's card and the chart's note behind "More about the air here" (`station-more-air`); the map's credits are behind its (i) (`map-credits` opens them, `wind-credits` is one element for a test, its lines its texts; `seeInCredits` in the tests opens, waits and closes). ## Conventions in the code

- **Venti's address is built in.** `AppServer.address` is `BuildConfig.VENTI_SERVER`, from the Gradle property `venti.server`; a debug build without it takes `http://10.0.2.2:8088` (the owner's own Venti on the Mac, as an emulator reaches it), a release build without it does not build. There is no setting and no other default. A UI test names its own server with the runner argument `ventiServer` (through `LaunchOptions.SERVER`); a test that names none has no server, which the screens show as Venti not reached.

- **"Continue with Google" is Credential Manager's, and a test's is the development server's.** `AccountModel.google` is `CredentialManagerGoogle` (`GetSignInWithGoogleOption` with `BuildConfig.GOOGLE_CLIENT_ID`, Venti's web client, from the Gradle property `venti.googleClientId`). A UI test launched with `LaunchOptions.GOOGLE_TEST_ACCOUNT` gets `DevelopmentGoogle`, which takes the token from `GET /v1/dev/google-id-token`; a release build ignores launch options. Where the server offers Google (`WindModel.googleSignIn`) the handle and password form stands behind "Sign in with a handle and password": a UI test opens it with `waitForThePasswordForm()`. The account row of the Google email is not one element: find the email with `hasAnyAncestor(hasTestTag("account-google-email"))`.

- **The "Continue with Google" button is Google's look, not the design pack's** (the owner, 2026-11-21: the official button). `account/GoogleButton.kt` draws it to Google's "Sign in with Google Branding Guidelines" (<https://developers.google.com/identity/branding-guidelines>, read 2026-11-21), as the custom button they allow: light fill `#FFFFFF`, stroke `#747775` of 1 px inside, text `#1F1F1F`; dark fill `#131314`, stroke `#8E918F`, text `#E3E3E3`; 40 high, a pill, 12 before the logo, 10 between logo and text, 12 after the text, the logo 20 high; Google Sans Medium 14/20. It is the one place in the app whose colours, sizes and font are not the pack's tokens: keep it so, and change a number only to what Google's page says. It stands on the account's page signed out (`account-google`) and in the dialog that deletes an account made with Google (`account-delete-google`); "Link Google" is a row of the list and stays the pack's. The button asks the phone for Google Sans (`DeviceFontFamilyName("google-sans")`), which the app does not bundle, and takes the phone's own font where it has none, as the emulators do (Roboto); that a phone of Google's shows Google Sans there is to verify. While the account works the whole button is dimmed, for which Google's page names no look.
  - *The logo.* `app/src/main/res/drawable-nodpi/google_g.png` is Google's "G", the file Google's page shows and hands out (<https://developers.google.com/static/identity/images/g-logo.png>, 200 by 204 pixels, fetched 2026-11-21, SHA-256 `d1ce9c2a…8638e6a`), byte for byte. It is Google's trademark, used under those guidelines for this button alone: never redraw, recolour, crop or tint it, and use it nowhere else. It is a picture and not a vector drawable because Google's "G" of today has a gradient with blurs (the SVGs of <https://developers.google.com/static/identity/images/signin-assets.zip> draw it with filters and a conic gradient), which a vector drawable cannot hold.

## How the build makes the core

Five tasks in `app/build.gradle.kts` build what the app takes from the rest of the repository and from its libraries; each runs again only when what it reads has changed:

| Task | What it does |
|---|---|
| `coreForAndroid` | `cargo ndk` builds `libventi_core.so` for each ABI in `venti.abis` (`gradle.properties`): `arm64-v8a` and `x86_64`. |
| `coreBindings` | Builds the core for the build machine and runs UniFFI's generator (the `uniffi-bindgen` program in `tools/uniffi-bindgen-swift`) on it to generate the Kotlin interface, package `fly.venti.core`. Settings in `uniffi.toml`. |
| `sharedAssets` | Gathers the sample flight, the map style, the bundled map region the fonts' licence and the core's notices (`licences/core-notices.txt`) from where the repository keeps them. |
| `googleNotices` | Reads `third_party_licenses.txt` and `.json` from every AAR of the release runtime classpath (Google's libraries carry them) and writes one `licences/google-third-party.txt`, one entry for each name. The reading is `GoogleNotices.java` in `buildSrc/` (plain Java, nothing to download), which the unit tests compile too (`GoogleNoticesTest`). |
| `designPack` | Takes the design pack into the build: its Kotlin tokens, the rest of its tokens as Kotlin, its fonts, its flying icons as vector drawables, the launcher and notification icons. |

Nothing they produce is committed: no generated Kotlin, no compiled core, no second copy of a shared file.

## What has never been tried

The app has run on an emulator in CI, driven by the UI tests, and on no phone. One test records a flight from made-up positions handed to Android as if its satellite receiver had found them, so the permission, the location manager, the recording service with its notification, the altitude conversion of Android 14 and later, and saving to the logbook all run there. What an emulator cannot show (recording with the screen off and battery savers, the altitude conversion against a known height, the pressure sensor as a vario, Bluetooth, the tone, "Open with" from real apps) is listed in [docs/architecture.md](../../docs/architecture.md#android). Besides that:

- **Flying.** The cockpit has only seen replayed flights.
- **The flight that records itself.** Tested against the core with made-up positions in the unit tests (stand, fly three minutes, stand), and on the emulator only with "Record now". A real take-off noticed by the core, a landing two minutes before the save with the screen off, and two hours of waiting are untried on a phone.
- **The cockpit's readings of 2026-11-22.** The landings handed to the core (`FlySession.handLandings`: the landings among the sites held around the glider, among the cockpit's take-offs, and the pilot's landing waypoints) and so the line under the second page's map (`nearest-landing`), the band "The wind carries you back" (`carried-back`), the speed-to-fly words under the climb and the rows of "Details" (`cockpit-details` on the third page) beyond "Altitude" have been seen on no screen: the sample flight's replay has no landing site near it, no pressure and no glider class. A site's page opened from Today speaks of the day chosen there (`SiteSheet.dayStartUnixS`); from the map, of its first day with flying hours.
- **The cockpit's pages.** The UI tests turn them with `turnTo("Map")` and end a session with `holdToEnd()`, a long press of 1.1 s on `cockpit-end`, whose hold is 0.67 s (`HOLD_TO_END_MILLISECONDS`, a second before 2026-11-23); the readings are found by their names ("Ground speed", "Wind", "Gained"), the wind's reading by `wind-reading`. The map's round buttons and the task's and the target's lines are on the second page, the lock, live tracking and "Record now" on the third.

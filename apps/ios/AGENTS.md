# Notes for AI sessions working on the iOS app

Working notes: what to know before changing the iPhone app or its tests. How to build it in CI, read its logs and look at its screenshots is in [CLAUDE.md](../../CLAUDE.md); what the app does is in [docs/design.md](../../docs/design.md) and [docs/plan.md](../../docs/plan.md); how it is built in [docs/architecture.md](../../docs/architecture.md#ios-first-target). The `README.md` beside this file is for people.

## Building and testing

- **When the owner's Mac is attached to the session, build and test there, not through CI** (the owner, 2026-11-21: a CI round is 40 minutes, the same test on the Mac is under two). If something on the Mac refuses a step, say so to the owner and wait for their word; do not fall back to pushing and waiting for CI. First, from the Mac's checkout: Homebrew's own `cargo` stands first on the path and has no iPhone targets, so run `apps/ios/scripts/build-core.sh` with rustup's tools first (`env PATH=/opt/homebrew/opt/rustup/bin:…`); then `apps/ios/scripts/build-design.sh` and `xcodegen generate` in `apps/ios`. Then **`apps/ios/scripts/ui-tests.sh`** runs the tests: with no names all UI tests, with names (`ui-tests.sh testA testB`) only those, `--unit` the unit tests first, `--unit-only` the unit tests alone (one simulator, no servers), `-n 4` on four simulators in place of three, `--first "iPhone 17e"` with that simulator first (the narrowest). It builds once, deals the tests out among the simulators as the workflow deals them among its machines, gives each simulator its own development server and made-up day on its own ports (8090/8091, 8092/8093, …), stops them at the end, and leaves the result bundles, logs and every screenshot under `target/apple/ui-tests/<run>/`, with one line per test at the end. All 22 UI tests took 12 minutes on three simulators on 2026-11-21 and under 10 on four (`-n 4`, the fourth an iPhone 17 on iOS 27.0), against 23 on one; the slowest part is the one with `testAFlightRecordsItself` (3.5 minutes). A list row that is a `Menu` opens only where its words are, not across the row: on the iPhone 18 Pro Max the middle of "Replay the sample flight" lay beside its words, and the test's tap opened nothing until its label was given the row's width (`.frame(maxWidth: .infinity, alignment: .leading).contentShape(.rect)`). Bringing newer commits onto the Mac's copy is the owner's to allow each time.

- Swift cannot be compiled in a cloud session. The `iOS` workflow builds the app, runs the unit tests (`VentiTests/`) and the UI tests (`VentiUITests/`) on a simulator, and uploads the screenshots as `ios-screenshots`, in light and dark appearance. When the build fails it keeps the full log as `xcodebuild-log`, or `xcodebuild-device-log` for the build for a real iPhone, whose result is `venti-unsigned-ipa`.
- The workflow has five jobs that run side by side: "Core bridge and app" (the bridge tests and the unit tests), "UI tests, part 1 of 3" to "part 3 of 3", and "Unsigned build for an iPhone", which is the quickest sign that the app compiles (about six minutes). Every test function of `VentiUITests.swift`, sorted by name, is dealt out to the three parts in turn, so a new test needs no entry in the workflow. Each part uploads `ios-screenshots-part-N`; a last job merges them into `ios-screenshots`. A part's build log is `xcodebuild-log-part-N`. One run takes as long as its slowest part, about twenty minutes (to verify after the first runs).
- The tests of the Rust-to-Swift bridge (`Packages/VentiCore/Tests/`) run on a Mac with `swift test`, without a simulator.
- **What the UI tests taught on 2026-11-21.** `isHittable` cannot be asked of an element that was scrolled out of a row: XCTest fails the test with "Failed to determine hittability"; compare the element's frame with the window's (`isOnScreen` in the tests). A tap in the middle of the map tab hits the development server's demo glider, which stands there: a test that wants what lies under it switches the layers of wind, sites and pilots off first and on again after (`setLayer`). A step that only adds a screenshot is written so that it cannot fail the test. A MapLibre property with a getter such as `isFillAntialiased` whose value is an expression keeps its own name in Swift, `fillAntialiased`; the name is in the header, not in the documentation's table.
- **A type of the core must not be named like a framework the app imports.** A record or an enum of the core is a type of that name in `VentiCore`, and such a type hides the framework's name wherever both are in scope. A record named `Observation` once stopped every model from compiling: `@Observable` writes `Observation.ObservationRegistrar`, and Swift found the record. `crates/core/tests/names.rs` holds the list of frameworks and fails on such a name; add a framework to it when the app starts importing one.
- **Venti's address is built in**, not a setting (the owner, 2026-11-21): the build setting `VENTI_SERVER` in `project.yml` reaches the app as `VentiServer` in its Info.plist and is read in one place, `VentiServer` in `App/VentiApp.swift`. A UI test names its own server with `--server`; one that needs none names `VentiUITests.nowhere` (`127.0.0.1:9`, where nothing listens), which the launch helper does by itself, so that no test asks the owner's Venti on 127.0.0.1:8088. The unit tests' host asks none.
- The UI tests that need a server run against `venti-server dev` on the same Mac. Its wind is six stations as they were on the evening of 18 November 2026, and its clock says that evening; its recorded forecasts are the runs of 06 UTC of 21 November, ICON-D2's two days and ICON-EU's four. Its demo account signs in as `demo` with `demo-pilot-password`, with three made-up flights, and keeps the group "Mustergruppe"; the other group, "Beispielgruppe", is joined with the code `5555-5555-5555-5555`. Its groups' plans are for 18 to 20 November, and the board lists plans from today by the iPhone's clock, so on a later day only a plan a test posts itself is there. The development mode hands out the small map region that comes with the app when it is started with `--maps apps/ios/Venti/Resources`.
- **A strong thermal day is made up.** The recorded forecasts are of late November: no thermals. `testTodaySaysWhatKindOfDayTheThermalsMake` runs against `tools/made-up-day/serve.py`, which stands in front of the development server and replaces every forecast's hours by a summer day's, for four days (the workflow starts it on port 8081 and names it as `VENTI_MADE_UP_DAY_SERVER`; without that the test is skipped). Which take-off gets how much heat depends on its coordinates, so the test's "Big day" holds for the recorded sites around the Tegernsee and would need a look if the sites were recorded again. Screenshots made with it show a made-up day: say so when showing them.
- The sample flight a new logbook offers is made up, generated by `venti-flight`, not a real pilot's.
- A number reaches the screen through `Format` (`Venti/Design/Format.swift`), which names the locale numbers are written in. Never call `.formatted()` on a number anywhere else: it follows the iPhone's region, and beside the core's words a screen then shows "2,5 km" next to "10.0 km NE". GitHub's simulators are set to the United States and do not notice; a simulator set to English in Germany does.
- By hand, without the script: `xcodebuild test` with `-destination "platform=iOS Simulator,id=…"`, `-derivedDataPath target/apple/DerivedData`, `CODE_SIGN_IDENTITY=-` and `-only-testing:VentiTests` for the unit tests. xcodebuild refuses a result bundle that is already there: give each run a `-resultBundlePath` of its own. The two servers of a UI run are a fresh pair every time, because the tests sign in and share, **and are stopped when the run ends**: on 2026-11-21 eighteen development servers of earlier runs were still listening on the Mac. A change is tested with the tests it touches and the unit tests.
- **Flights for a UI test.** The tests tap "Add a sample flight" for one flight. The launch argument `--sample-logbook` (`LaunchOptions` in `App/VentiApp.swift`, beside `--sample-waypoints`, `--sample-airspace` and `--sample-task`) starts the app with the sample flight five times more, on other days of July 2026: ten thermals, which is what "How you fly" needs before it says anything (`testHowYouFlySaysWhatTheTracksShow`). Without the argument it does nothing.
- **The made-up day has the development server's days.** `tools/made-up-day/serve.py` dates both its thermal map and its forecast for a place from "today" by the development server's clock (18 November 2026), which is the clock the map tab and Today name their days by; the forecast's own screen chooses and names "Today" by Venti's clock too (`ForecastScreen.today(among:at:)` with `wind.serverNowIfRead()`, 2026-11-22; before the server's time is read no day is "Today" and the first is chosen). Today offers as many days as the forecasts reach, four at most, and three where four names do not fit whole: on the iPhone 17e at the text size above the largest standard one "Tomorrow" was cut to "Tomorr…" (`testTodaysDaysFitWithLargerText`, whose launch argument `-UIPreferredContentSizeCategoryName` sets the text size). A test that goes from a square of the map to its forecast finds the map's day in it only because the two have the same days.
- **The design language** (`design/`, at the repository's root) reaches the app three ways, none of them a copy: `project.yml` compiles `design/tokens/VentiTheme.swift` into the app and bundles `design/fonts/*.ttf` (named in `Info.plist`), and `scripts/build-design.sh` gathers the app icon, the flying icons, the logo and the art into `Venti/Resources/Design.xcassets`, which git ignores. Run that script before `xcodegen generate`, and again when the pack changes; the workflow does.
- **How a screen wears it.** A list is `VentiList { }`, never `List { }`: it puts the page's ground behind and the card's surface under the rows. A colour is a role, `.foregroundStyle(.venti(.danger))` or `.background(.venti(.surface))`; where a `Color` is asked for by type, `Color.venti(.danger)`. Text is `.font(.venti(.headline))` for what the system has a text style for, or `.font(.ventiType(.hero))` for the pack's own styles; never `.font(.headline)` and never `.system(size:)`. A button is `.buttonStyle(.venti(.primary))`, `.quiet`, `.accent` (one a screen at most: what starts or records a flight) or `.danger`. What floats over a map is `.ventiFloating(in: .capsule)`; there is no glass and no material. `.secondary` and `.tertiary` mean the pack's secondary and muted ink, because the root sets them. Search a diff for `Color(`, `.system(`, `List {`, `Material` and `glassEffect` before pushing.
- **The cockpit is in the flight theme.** `CockpitScreen` and every sheet it opens end in `.ventiFlightThemed()`: the flight theme's colours, a light appearance whatever the iPhone is set to, buttons 64 points high (`\.ventiInFlight`), and an edge in place of a shadow on what floats. A sheet added to the cockpit needs the modifier on its content, or it is drawn in the app's theme over a white cockpit. In the cockpit write a role, `.venti(.textSecondary)`, and not `.secondary` or `Color.venti(...)`: inside a plain button the first is the system's grey, and the second knows light and dark but not the flight theme. Readings are `Reading` in `CockpitScreen.swift`, at fixed sizes; nothing there is under 14 points. The pages are `CockpitPage`; a UI test turns them with `nextPage(in:)` and ends the cockpit with `endTheCockpit(in:)`, which holds the button.
- **What is drawn on a map** takes its colour from `Palette` (`inkOnMap`, `haloOnMap`, `accentOnMap`, `goodOnMap`, `quietOnMap`, the own position's pair), which are the light theme's tokens: the map is light in both appearances. A literal `UIColor(hex:)` or `.white` in a map layer is a colour that is not a token. Over a map, a control is `VentiChip` or a button in `.buttonStyle(.ventiRound)`, and a panel is `.ventiFloating(in:)`; there is no glass.
- **A choice between a few things side by side** is `VentiSegmented(options:selection:)`, the pack's pill, and never `Picker` with `.pickerStyle(.segmented)`. A binding that starts a task when it is set gets a name of its own (a `private var` on the view): written in place, in the call, the compiler cannot type it.
- **The aerial view** is `AerialButton` on a screen and `aerial:` on its map (`OverviewMap`, `FlightMap`), both reading `Preferences.mapShowsAerial`: one choice for every map. `MapSetup.showAerial` shows the layers `map/style.json` marks `venti:view: aerial` and hides those marked `drawn`; a new map takes the parameter and calls it in `didFinishLoading`, as the two do. `CockpitMap` takes it too, but `CockpitScreen` hands it on only off the first page, and the cockpit's button is `CockpitAerialButton` (64 points, no `.ventiRound`) with the identifier `cockpit-aerial`; the cockpit's dark lines have casings that `CockpitMap.Coordinator.casings` shows only while the photographs do. The choice is kept between launches and the UI tests do not reset preferences, so a test that switches it on switches it off again, and starts by looking which way it stands. The photographs come from the network: only `testTheMapWithTilesFromTheNetwork` shows them.
- **The forecast map** (the kind of day, square by square) is `ThermalMapModel` (`Forecast/`), `ThermalMapLayers` and `ForecastCard` (`Map/`). Its fill layer is put under the style's cable cars, borders and names by their layer names (`ThermalMapLayers.over`): a style that renames them puts the squares under its first names instead. The chip's choice is kept between launches like the aerial view's, so `testTheMapShowsTheKindOfDaySquareBySquare` switches it off at its end and starts by looking which way it stands; a test that leaves it on puts the card over the map of every later screenshot. Its tap in the map's middle opens a square's sheet only where the stand-in's map has a square there and nothing else lies over it, so the sheet is checked only when it comes.
- **The forecast map's card and its tests.** The card shows the layers, the days, the line of hours and one line of words; the key, the model's run and the notes are behind "Key and notes" (`forecast-more`, whose value is "Shown" or "Hidden"), closed whenever the card opens, so a test that wants `forecast-key` or `forecast-model` opens it first (`showKeyAndNotes`). The line of hours is one element (`forecast-hours`, its value the hour, "The whole day" on "Day"): a test chooses an hour by what the strip then says (`chooseHour`). The launch argument `--map-at <lat>,<lon>,<zoom>` opens the map tab's map there; the hours' tests frame the made-up squares with it, all nine by five above the card. `testTheForecastCardFitsWithLargerText` is the first by name of the forecast map's tests, so `ui-tests.sh --first "iPhone 17e"` with those tests puts it on the narrowest simulator. The unit test that times a step of an hour (`testAnHourOfAWholeRegionIsQuickToDraw`) is skipped by `ui-tests.sh --unit`, which names no stand-in to the unit tests: start a development server and `tools/made-up-day/serve.py` by hand on two free ports and run `xcodebuild test-without-building … -only-testing:VentiTests/ThermalHoursTests` with `TEST_RUNNER_VENTI_MADE_UP_DAY_SERVER` naming the stand-in. On 2026-11-21, on a simulator, a step took 7 ms for a region of 78 by 22 squares with an arrow in each (the core's two texts and MapLibre reading them; what MapLibre then takes to draw is not in it).
- **The weather along a drawn route** is `RouteWeatherModel` and `RouteWeatherSection` (`Task/RouteWeather.swift`, `RouteWeatherViews.swift`), folded under the legs of `RouteMapPlanner`'s card (`route-weather-toggle`, value "Shown" or "Hidden"); the card scrolls once it would take more than 60% of the planner's height. The days are the thermal map's (`ThermalMapModel`, asked for when the section opens if the map tab has not), the start the next full hour by Venti's clock in steps of 30 minutes, the speed 20 km/h in steps of 5, the glide the settings' in steps of 0.5. The model asks the core's `routeWeatherPath` once for a route and a day (a new start or speed reads the held answer again through `routeAlong`, without asking), then brings the ground under the route through `TerrainModel.ground(covering:)`, the same as a flight's profile; with the map that comes with the app that is its archive, which reaches only round the Tegernsee. Every word of the weather is the core's. `--map-at` opens the planner's map there too. `testARouteShowsTheWeatherAlongIt` draws three places by the Tegernsee and waits for a departure height in metres, light and dark.
- **The rain radar** on the map tab is `RadarModel`, `RadarCard` and `RadarLayers` (`Map/`). The model asks for the list while the chip "Radar" (`radar-chip`, off until switched on, kept like the forecast's) is on and the app in front, every five minutes, and reads the answer it has again every minute through the core, so that "4 minutes ago" and the stale sentence stay true without asking; the ages are counted by `wind.serverNow()`, as everything else is, which is why the development server's frames stay four and nine minutes old on any day. It draws every layer of the answer along one line of time, and holds no rule about which frame lies under which: the card's strip has a cell for each of the core's `moments`, opening on `firstMoment`, and for the chosen moment the model takes each of its `frames`, bottom first, fetches the picture at `layers[layer].frames[frame].path` (kept as the server sent it, by its path, for this run of the app: a step to the next moment asks only for the radars' picture, the analysis under it being the same), and has the core colour it (`radarFrameImageUnder`) with what the source did not see as the veil where the moment's frame says `drawsUnseen` and fully clear (`RadarColours.clear`) where not, handing it as `above` the server's pictures of the frames after it in the moment, so that it comes back clear wherever one of those sees, rain or dry: a place has the word of the topmost picture that sees it, and where both have rain the colour is the key's, not a deeper one. No coloured picture is kept: the same frame of the analysis is another picture under another frame of the radars, so each moment's are coloured anew from the kept ones, and a `RadarPicture` is named (`id`, by which the map draws it again only when it is another) by its frame and the paths of the frames over it (`above`). A moment is put on the map whole or not at all: while one of its pictures cannot be had, those of the moment before stay with their own line (`shownMoment`). The card's caution is `RadarModel.caution`, the `staleWords` of the topmost layer that has frames; the credits, at the map by name and in full behind "Key and notes", are those of the layers drawn (`drawnLayers`, the topmost first), and "Key and notes" begins with a line a layer saying what it is (`radar-layers`, the core's `what`). A Venti without radar (501) is the state `.none` with the core's sentence, said on the card without "Try again". A picture is the server's PNG with the palette the core writes into it (`RadarColours.palette`: the key's six tokens and the forecast map's veil, all solid) as an `MLNImageSource` of its own under a raster layer of its own, both named `rain-radar-` and the source (`RadarLayers`), with `rasterResamplingMode` "nearest" and the opacity of the forecast map's squares (`ThermalMapLayers.opacity`), the first put above the forecast's squares and so under the base map's names and all the app draws, each further one above the one before; a source and its layer are added with the layer's first picture and taken away when a moment has none of that layer, or the radar is off. Each raster layer has that opacity for itself, which is why the lower picture must be clear where the upper sees: two see-through layers would add up. The card's strip is `CellStrip`, the forecast's hour strip made general (`ForecastHourStrip` is now a thin wrapper around it): up to six moments have their time in the cell, more have empty cells and the times of every third or sixth under the strip (`RadarStrip.named`), which no UI test shows, the development server having two moments; `RadarTests.testTheStripOfTwoHoursOfFramesIsKeptAsAPicture` renders 25 and keeps the picture in the unit tests' result bundle (`xcrun xcresulttool export attachments --path …/unit.xcresult`). `KeyAndNotesButton`, `MapKeyLine`, `CardCaution` and `CardProblem` (`Map/MapCardParts.swift`) are what the two cards share. The tests: `testTheMapShowsTheRainRadar` (`--map-at 46.3,13.3,5` shows the whole of both pictures, which have the same box, with the analysis where the radars see nothing, over the map's bare ground, since the map that comes with the app ends long before; the recording is of 13:19 UTC on 2026-11-21, and the times in a line are the simulator's time zone's, so the tests look at a line's form), `testTheRainRadarsCardInTheDark`, `testTheRainRadarSaysWhenVentiIsNotReached`; each switches the chip off at its end. No UI test reaches a Venti without radar, a stale layer, or a moment with one layer only: the unit tests hold them.
- **The filter of the flying sites** is the core's (`filterSites`, `sitesFilterChoices`): `SitesModel` keeps the pilot's choice (`SitesChoice`, in the preferences `VentiMapSites…`, only where it was given a store, which the unit tests' models are not), asks the core when the sites, the choice or the measured wind change, and holds the answer as `filtered`; the map draws `filtered.fitting` and, muted and without names, `filtered.unsaid` (`SiteSymbols.picture(for:isUnsaid:)`, the pack's disabled pair, in the same symbol layer under the others by `rank`), and `SiteList` has the two as sections. The control is `SitesFilterForm` (`Sites/SitesFilter.swift`): a sheet at half height from the row `sites-filter` of the map's layers sheet, the same form pushed in the list, and `sites-filter-line` over the map's credits while a filter is on. "Measured now" is offered while `SitesModel.measuredNow` finds a station with a current direction near the map's middle (the core's `stationsNear` gives the order); "Forecast now" is not offered, the app having no forecast at hand for the map's middle. The wind's sixteen points are a `VentiSegmented` that scrolls and opens at the chosen one; a test brings "S" into the row by dragging `sites-wind`. A site mapped as an area is drawn by `SiteFields` (`Map/`) under the signs, only while its box is larger than the sign at the map's scale, looked at again with every move of the map. The choice is kept between launches and the UI tests do not reset preferences: `testTheSitesFilterShowsWhatFitsAndWhatSaysNothing` launches with `--all-sites`, which starts with a filter that asks nothing and keeps that, and its teardown launches so once more. The map that comes with the app has no ground at zoom 15: the close-ups of the two fields stand on bare paper.
- **Adding, correcting and confirming a site, in two tiers** (`Sites/SiteEditing.swift`, `Sites/SiteEditScreens.swift`). Venti's own sites are the partners' (`venti`) and the crowdsourced ones (`venti-pilots`); who may do what with which is the core's, and the app asks it and holds no rule: `AccountModel.offers(for:takesSitesFromPilots:confirmations:)` (the core's `siteOffers`) for a site's page, `AccountModel.historyOffers(_:takesSitesFromPilots:)` (`siteHistoryOffers`) for its history, `AccountModel.adding(takesSitesFromPilots:)` (`siteAdding`) for the entry and the form of a new one, and `siteCorrecting(site:)` for the form of a correction. Both read the account the core stores, and `AccountModel.read()` (`accountRequest` / `accountRead`) brings that up to date when the app comes to the front (`RootScreen`) and when the account's page opens; an ended session is no error there. `SiteEditing` sends the core's requests with the account's token, as the groups' are sent, and reads a site, its history and its confirmations without one. **The switch** "Places from pilots" is `SitesChoice.withPilots` (the preference `VentiMapSitesFromPilots`, off by default) at the foot of `SitesFilterForm`, with the filter's own words (`SitesFilterChoices.withPilotsWords` / `withPilotsAbout`), and it is handed to the core as part of the filter (`SitesFilter.withPilots`): the core chooses the path (`sitesPathFor`), says that a filter is on (`filtered.isOn`, which the map's button, the line over the credits and the list read) and ends the filter's words with it; the app has no OR and no choice of path of its own. Switched off, the places from pilots go from the model at once and the server is asked anew. `--all-sites` switches it off with the rest. **A crowdsourced site is marked** with the core's `label`: under its name on the map (`OverviewMap.Coordinator.siteLabel`), first in a row's second line (`SiteRow`), and under the name on its page (`site-tier`), where a partner's site says "From a partner" too; the pin is the one of its use, the pack having none for the tier. **A site's page** has `SiteConfirmSection` under the facts (the count, which opens `SiteConfirmationsScreen`, or the core's line that nobody has said so yet, `site-confirmations-none`, which the core leaves empty for a landing: the list is read with `siteConfirmationsOf`; "I took off here and it was good", which opens `SiteConfirmSheet` at full height, its line being typed over a keyboard; once said, the core's sentence with "Change the day" and "Take my confirmation back"), the tier's notice over the description (`site-tier-note`, said once: the credit of Venti's two layers has no notice), the description under the core's heading (`SiteView.descriptionTitle`), and `SiteByPilotsSection` at its foot: correct, remove, history and report as offered, and the core's one line about what is not (`site-offers-note`). `SiteConfirmationsScreen` shows the list the page has until it is read anew, a spinner while it has none, the core's words with "Try again" where it cannot be read (`site-confirmations-problem`), and `notWholeWords` under the list. **A site removed on its page** has no flag in the app: after the removal the page reads the site's history (`SiteEditing.wholeHistory`) and goes on with the last revision's site, which the core marks as removed (`byPilots.isRemoved`), so that `siteOffers` answers for it: the history alone, and the line "This site was removed: it is on no map." Where the history cannot be read just then, the page stays as it was until it is opened again. The page does not show `SiteOffers.bringBackWords` as an entry of its own: bringing back is in the history. The sheets and alerts of a section hang on one of its rows, because a section hands what hangs on it to every row. The confirm sheet's "today" is `wind.now`, Venti's clock, on the iPhone's calendar (`SiteDay`): the server counts a confirmation's day from its own date, and the development server's is 18 November 2026, so "Yesterday" there is the 17th. **The entry for adding** is in the bar of what a long press on the map opens (`PressedPlaceSheet`), not where a site's sign lies under the finger: `add-site-here` with the core's `entryWords` for a pilot of the crowdsourced tier; none for a partner, who adds on the website; the rule is the core's and the same in the three apps: the entry is shown whenever `entryWords` is not empty, and it opens the account where `leadsToSignIn` (signed out on a Venti that takes places from pilots; the identifier is then `add-site-sign-in`), else the form; none where Venti takes nothing. `SiteEditForm` is one sheet for a new site (`init(adding:at:)`, with `SiteAdding`'s title, sentence, notice and button) and a correction (`init(draft:of:correcting:)`, with `SiteCorrecting`'s, which follow the site's tier): the core's fields in the core's order, the uses and the sixteen points as pills to tick (`SiteChoices`), the place in numbers with "Move", the faults under their fields from the first try to send. A correction refused because someone else changed the site (`SiteEditing.Refused.wasChanged`, the core's `siteWasChanged`) reads the site again and hands base, draft and site to the core's `siteDraftRebased`: the form goes on from its draft with its words, what the others changed, the clashing fields' titles marked and the core's sentence for each under its field, where a fault's stands (`clashesInWords`, `site-clash-words`); the app has no merge of its own, and no UI test shows a clash. The history (`SiteHistoryScreen(id:)`, which needs the identifier alone) reads its pages with the last revision of the page before and shows what `siteHistoryOffers` offers: "Bring this site back" on a removed site, "Undo the last change", a row's own `putBackWords` where it `canBePutBack`, "Report this revision", and the core's line about what is not offered (`site-history-note`). - **The words of a screen are the core's** wherever it gives them (`screen_words.rs`): `mapLayersWords()` (the layers sheet's title, its two headings, every layer's and row's name, the four chips' names, "Credits" and the base map's and the terrain's credit), `commonWords()` ("Done", "Cancel", "More": used in the screens of 2026-11-22, not yet everywhere), `pagesWords()` (the settings' row "Glider and cockpit"), `siteSheetWords()`, `stationSheetWords()`, `cockpitDetailsWords()` (not the wind's row, for which it has no name), `gliderWords()` and `gliderClassName`, `todayWords()` (the hour strip's note), `plannerWords()`. Today's card and rows show `nearbyShort`; the long `nearby` is on a site's page.
- **A route as GPX** is in the planner's "More" menu (`route-more`, `RouteMapPlanner`): "Export GPX" hands the core's `routeToGpx` to the system's sheet that saves a file (`GpxFile`), "Import GPX" reads any file picked with `routeFromGpx`, whose `words` stand in place of the route's until the route changes. The two file dialogs hang on two different views, since two on one view do not both open. No UI test picks a file.
- **An empty screen** is `VentiEmpty(title:text:)`, with its buttons in the trailing closure: the pack's valley over what is not here yet. It is for a place where nothing has happened yet. Something that went wrong keeps `ContentUnavailableView` with `Image("icon-caution")` and no art. The app is called Venti in what it says to the pilot, never "your Venti server": there is one Venti.
- **One thing is presented at a time.** A cover or sheet asked for while an alert is going up does not open, and SwiftUI does not try again: the state says "open" and nothing is on screen. That is how an alert about the position kept the cockpit shut. Do not raise an alert for something that is not yet a fact, and open the cockpit from another tab only through `AppNavigation.startFlight()`, which the Fly tab answers once it is on screen.
- **The home-screen widget, "the next days at my take-off"** (`VentiWidget/`, a WidgetKit extension; `Venti/Widget/`). It links no Rust and asks no server: it draws `TakeoffSnapshot`, a file the app writes into the folder the two share (the app group `VENTI_APP_GROUP` of `Config/Base.xcconfig`, `group.` and the bundle identifier, named in both targets' entitlements and Info.plists; `TakeoffSnapshotStore.shared`). `Venti/Widget/Shared/` is compiled into the app and the widget (the snapshot, the face `TakeoffDaysView`, the words); the widget target takes `Theme.swift`, `Components.swift`, `Format.swift`, the tokens and the fonts besides, and a catalogue of its own with the pack's four signs it draws (`VentiWidget/Design.xcassets`, gathered by `scripts/build-design.sh` and not committed). `TakeoffWidgetWriter` (app only) writes: after every load of Today (`TodayModel.onLoaded`), when the app leaves the screen where a take-off was kept or forgotten or the reading is older than Today keeps one, and in a background refresh of its own every four hours or so (`….widget-days` in `BGTaskSchedulerPermittedIdentifiers`); then it asks WidgetKit for a new timeline. Which take-offs are in it is the core's `todayTakeoffs` without a place (the pilot's own, the first six by name: the first is the widget's until the pilot chooses another in its setup, `ChooseTakeoff`), and a day's name, status and line are the core's `siteOutlook`, asked through the same two functions Today asks by (`TodayModel.forecastAnswer`, `outlook(of:in:nowUnixS:)`). **The widget cannot ask the core what a day is called tomorrow**, so the app asks twice: an `Edition` is the days as the core names and judges them from a moment on, one for now and one from the next day's first moment, and the widget shows the edition whose time it is. Past the last edition, or a day after the reading (`goodForS`), it says the forecast is too old in place of the days; it never shows a day under an older name. The widget ages by the iPhone's clock, having no other: against the development server, whose clock stands on 18 November 2026, every snapshot is out of date at once. The words the core lacks are in `Venti/Widget/Shared/WidgetWords.swift` alone, with the setup's intent and entity, whose titles the system reads out of the build and so have to be literals where they are used. A tap opens `venti://today` (`RootScreen.onOpenURL`). Under test the app writes nothing into the shared folder (`LaunchOptions.isUnderTest`). The widget's process is reached by no test: `TakeoffWidgetTests` draws the same face in the unit tests' host, small and medium, light and dark, each state, and keeps the PNGs in the result bundle; `ui-tests.sh --unit` puts them beside the UI tests' screenshots. It has stood on a simulator's home screen once, on 2026-11-22, put there by a throwaway UI test that drove the home screen (long press, "Edit", "Add Widget", search "Venti", the button whose label ends in "Add Widget"; the widget is then an icon with the label "Venti" and the value "Widget"): both sizes drew a snapshot laid into the simulator's shared folder by hand (`xcrun simctl get_app_container <udid> <bundle id> groups` names it), the app started by hand wrote its own and the widgets followed, and a tap opened Today from the Map tab. That test is not in the suite: the home screen's controls are another iOS's on GitHub's machines. On no phone yet. A simulator grants the app group without a team; an iPhone needs it on the developer account and in the profiles of both identifiers (`VENTI_PROFILE`, `VENTI_WIDGET_PROFILE` where signing is manual).
- **The cockpit has its airspace before take-off, whatever the map tab draws** (2026-11-22). The map tab's airspace is off until switched on and then asks nothing, so the Fly tab asks by itself: `FlyScreen` has a `PilotPosition` (read without asking once the pilot has allowed the position, on Today or in the cockpit) and a `.task` named by the place to a tenth of a degree (`AirspaceModel.askedKey`) that calls `AirspaceModel.keepCovered(around:)`; `CockpitScreen` has the same task on the glider's position, waiting for the take-off and in flight. `keepCovered` is `refresh(around:)`, whose rule for when to ask is the core's (`keptAirspaceIsDue`: nothing kept, a day old, or within 0.75 degrees of the kept area's edge), and where the server could not be asked it asks again after `retryAfter` for as long as the task runs. What came is kept by the core (`keepServerAirspace`) for a flight without a network. `Preferences.mapShowsAirspace` is only what the map tab draws. A pilot who has allowed the position nowhere has no airspace from Venti until the cockpit is opened, which asks for the position. `testAirspaceComesFromTheServerByItself` keeps the map's airspace off from start to end, allows the position on Today ("Use my position") and resets that at its end.
- **Foehn on Today** (`Today/FoehnModel.swift`, `FoehnViews.swift`; the core's `foehn.rs`). `TodayScreen` owns a `FoehnModel` and asks when Today has its take-offs and on a pull (`anew`); the model sends the core's `foehnPath`, hands the answer to `foehn` with the take-offs' places and `wind.serverNowIfRead()`, and reads a held answer again for ten minutes without asking. `FoehnTodayLine` (`today-foehn`) stands over the take-offs only while `todayLine` is there, on the caution's or the danger's soft ground by its level; `FoehnFootRow` (`today-foehn-row`) is the page's last row and opens the same `FoehnSheet`: a section for each pair (`foehn-row`, `foehn-level`, `foehn-words`, `foehn-when`, `foehn-chart` with Swift Charts, zero in the middle by `FoehnChart.reach`), then `foehn-explanation`, `foehn-caution`, `foehn-credits`; `foehn-problem` with "Try again" where Venti is not reached, and then Today has no line. The app's own words here are two, because the core has them only with an answer: the title until the first answer (`FoehnModel.titleUntilRead`) and "Venti could not be reached for foehn." `testTodaySaysWhenFoehnIsLikelyAndShowsThePressures`, light, dark and with larger text; `FoehnModelTests`.
- **`testAPilotSignsInAndSharesAFlight` puts the demo flight's sharing back** to what it was: the development server's notifications and feed name the demo pilot's newest flight as a public one, and left "with a link" the tap on "commented on your flight" in `testThePilotsScreensInTheDarkWithLargerText` opened no flight when both ran against one server.
- Never commit a certificate, a provisioning profile or a team ID: they belong in `Config/Local.xcconfig`, which git ignores.

## What has never been tried

What a simulator cannot show (recording for hours in the background, the vario connecting and reconnecting, the tone) is listed in [docs/architecture.md](../../docs/architecture.md#ios-first-target). Besides that:

- **A flight that records itself.** The core's rule is tested with made-up positions, and the UI test `testAFlightRecordsItself` flies one on the simulator: it sets the simulated iPhone's position once a second (`XCUIDevice.shared.location`), stands, flies, stands, and finds the flight in the logbook. The positions wander by half a metre because the simulator hands a position on only when it differs from the last. Nobody has taken off with it, and it has not run with the screen off.
- **Flying.** The cockpit has been tested with replayed flights on a simulator. It has not flown, and nobody has connected a real vario to it. What is worked out from the flying itself (the wind in strong wind, the thermal's picture, the landing within reach, the line about a strong wind) has only ever seen a made-up flight.
- **Live tracking** has talked to the server's own example answers and to no server.
- **The assistant** has only talked to a scripted stand-in in tests, never to the real service.
- **Scanning a task's QR code with the camera** has not been tried on a phone.
- **Signing in, sync, sharing and the airspace fetched from a server** were tested against the development mode in a simulator, on no phone.
- **Sending a flight to the DHV-XC.** Built against the specification in the DHV-XC's rules and its two example answers. Nothing has been sent to the DHV-XC: no test may, and a UI test never taps "Send".
- **Downloading a map region.** No real region has been built. A download runs only while the app is open.

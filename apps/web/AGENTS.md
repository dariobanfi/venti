# Notes for AI sessions working on the web app

Working notes: what to know before changing the app or its tests. What the app does and what is not built is in [docs/plan.md](../../docs/plan.md) and [docs/design.md](../../docs/design.md#web), how it is built in [docs/architecture.md](../../docs/architecture.md#web) (the core in a worker, storage in IndexedDB, wind, account, airspace, sites, forecasts, live, everyone's flights, reports, plans, the ground under a flight, how it is tested). The `README.md` beside this file is for people.

## Checks before a push

- From `apps/web`: `npm run check && npm run format:check && npm run licences && npm test`, then `npm run build && npm run test:e2e`. After a change to `crates/core`, `crates/core-wasm` or anything below them, `scripts/build-core.sh` first: the tests run against the module that was built last. `npm run format` rewrites what `format:check` complains about.
- **The npm packages are held to what the owner's Mac can install.** Its npm registry is a mirror that lags npm's own by weeks, and has some packages not at all; never point npm at another registry. So `package.json` pins the newest version the mirror had (2026-11-21: SvelteKit 2.65 rather than 3.4, Vite 8.3.5, MapLibre 6.14, svelte-check 4.5.0, whose later versions need `@sveltejs/load-config`, which the mirror lacks). Before adding or updating a package, ask on the Mac with `npm view <package> versions --json` and pin a version it lists. The mirror's metadata leaves out each package's licence, so a lock file resolved through it fails `npm run licences`. To write the lock: `npm install` on the Mac; fill each entry's `license` (and `funding`) from the package's own `package.json`; replace the mirror's address in every `resolved` with `https://registry.npmjs.org/` (the tarballs and their hashes are the same); `npm install --package-lock-only` to let npm write it in its own form; then check that the mirror's host name is nowhere in the lock file, which is public and from which CI installs. `npm ci` on the Mac then installs from the mirror by itself, because npm swaps npm's own host for the configured registry.
- **The browser tests do not run natively on the Mac** (2026-11-21); everything else does, `scripts/build-core.sh` included. The browser that `npx playwright install chromium` downloads is killed by the Mac's binary allowlist (Santa) when it starts, so the browser tests run in a container: `scripts/checks-in-a-container.sh e2e`, which also runs licences, formatting, types and unit tests first (without `e2e`, only those), and arguments after `e2e` go to Playwright (`e2e --project=phone-light`). It builds the `site` stage of `deploy/web.Dockerfile` from the checkout, and for the browser tests an image on top with Chromium and Inter, which Docker keeps until Playwright's version changes. It mounts `crates` and `apps/ios/Venti/Resources` read-only, because the tests read the server's golden files, the sample flight and the region's elevation tiles, which the image does not hold, and `screenshots` and `test-results` writable, so that they land where a run on the machine puts them; nothing else of the checkout is written. For the browser tests it starts `target/debug/venti-server dev` (as built last) and `tools/made-up-day/serve.py` on the Mac, on ports 8290 and 8291 (`VENTI_CHECKS_PORT`), which the container reaches as `host.docker.internal`, and stops them at the end. Docker needs Claude Code's sandbox off. It takes at most 6 processors (`VENTI_CHECKS_CPUS`) and runs 4 browsers at a time unless given `--workers`: uncapped, it took 17 of the Mac's 18 and starved the emulators and other sessions' builds. Run the spec files a change touches, in one project where four add nothing; the whole suite is run once, at integration, when nothing else runs. Uncapped, a full run took 8½ minutes on 2026-11-21.
- The first run of `scripts/build-core.sh` installs the `wasm-bindgen` tool in the version `Cargo.lock` names, which takes a few minutes. Its last step, `scripts/strip-core.mjs`, removes from the module what only the phones use.
- The browser tests need a Chromium that Playwright can drive: `npx playwright install chromium`, once.
- The browser tests take about a quarter of an hour on four cores, for 260 tests at four widths and appearances. One file at one width is quick: `npx playwright test e2e/plans.spec.ts --project=phone-light`; one project: `npm run test:e2e -- --project=phone-light`.
- They start `venti-server dev` with `cargo run` (which compiles it the first time) and use one that is already running. Another session's server on port 8080 holds what that session's tests left in it: name a port of your own for the tests, `VENTI_DEV_SERVER=http://127.0.0.1:18431`. Build the server with the same `CARGO_PROFILE_…` settings in the environment as the tests run with, or `cargo run` builds it again.
- `npm run dev` and `npm run preview` pass `/v1` and `/f` on to `http://127.0.0.1:8080`, or to `VENTI_DEV_SERVER`. Without a server there the map says that the server could not answer.
- The preview the tests start listens on port 4173 and on no other (`playwright.config.ts`), so two sessions cannot run the browser tests on one machine at the same time. Not tried.
- The tests keep a screenshot of every screen in `screenshots/<project>/`, for four projects: a phone's width and a desktop's, each light and dark.
- The `Web` workflow runs all of it on every push that touches the app or the core. Its artifacts: `web-screenshots`, `web-site` (the built site, the folder to serve once the owner decides to publish the app; nothing publishes it now) and, when the browser tests fail, `web-test-results`. Download with `gh run download <run> -n web-screenshots`.
- The workflow takes 35 to 45 minutes, most of it the browser tests, which are slower on GitHub's machines than here. It lets a run that has started finish; of the runs waiting behind it only the newest is kept, so a push is often tested together with later commits. Look for the newest finished run that holds the commit, not for the commit's own.

## The core for the browser

- **After a change to the core or its binding:** `scripts/build-core.sh`, then `npm run check`. A record that gained a field is a type error in the hand-built test records until they have it.
- **A reader in which the pilot is "you" needs the account first.** The core tells whose a plan or a group is by the handle of the stored account, and takes any failure to read that file for "signed out". Over the browser's storage a file is fetched on request, so after a reload such a reader would call nothing the pilot's own. `crates/core-wasm` therefore reads answers about groups through `Session::call_as_the_pilot`, which looks at the account first: the call then fails for want of the file, and the session fetches it and calls again. Bind a new reader of that kind the same way, and test it over a store that was reloaded, as `src/lib/core/groups-source.test.ts` does.
- **A record the page hands back to the core** needs `serde::Deserialize` under the core's `wasm` feature, as `TrackPoint` and `PlanDraft` have. One that only comes out needs `Serialize` alone.
- **An object of the core that holds much is freed by hand.** `Terrain` holds half a megabyte of heights for each tile it was given. `src/lib/core/terrain-source.ts` makes one for a flight and frees it with the answer.
- **Which take-offs Today lists, their order and the best of a day are the core's** (`Core.todayTakeoffs`, `todayOrder`), asked through the worker (`todayTakeoffs`, `todayOrders`): a pure function of the core is a call to the worker too, since the page does not load the module. `src/lib/today/order.ts` only hands over how each take-off stands and lays the answer over them. Which day Today opens on (`firstDay`) is still the app's own rule, as on the phones, until the core has it.
- **The pilot's own sites are files of the core** (`sites-kept/`), so keeping, forgetting and Today's refresh of a kept site go through `CoreSession.change`, which stores what the core staged; `src/lib/core/today-source.test.ts` reads them back over a store that was reloaded. `KeptSitesModel.revision` counts the changes: Today asks for its take-offs anew when it has gone up.
- **Venti's two tiers of sites** (the partners', `venti`, and the crowdsourced one, `venti-pilots`: adding a site, correcting, removing, their history, and "I took off here and it was good") are the core's from who may do what to every word and refusal (`crates/core/src/site_edit.rs`, `site_offers.rs`); the worker's side is `src/lib/core/site-edit-source.ts`, the page's `src/lib/sites/edit.svelte.ts` (the core's words, what may be added from here, and a draft while its form is open), `SiteEditForm.svelte`, `SiteHistoryView.svelte`, `SitesRemovedView.svelte`, `SiteConfirmSheet.svelte` and `SiteView.svelte`; the map tab (`src/routes/map/+page.svelte`) wires them. **The app keeps no rule about who may do what.** A site's page asks `Core.siteOffers` (through `SiteEditsModel.offers`) and shows what is offered in the core's words, with its one note; the entry for adding, the form's title, notice, sentence of giving and button are `Core.siteAdding`'s (`SiteEditsModel.adding`), so the demo account, a partner, reads "Add a site" and every other pilot "Add a place pilots take off from". The entry is shown wherever the core has words for it (`entryWords`): on the map's controls and under a place chosen on the map. Where it `leadsToSignIn` (nobody signed in, on a server that takes places from pilots) it is the core's sentence "Sign in to add a place pilots take off from." as a link to the account; where the words are empty there is no entry. A correction's form takes the same four from `siteCorrecting` for the site it was made from (`SiteDraft.correcting`), which follow the site's tier, whoever corrects it. Both answers follow the account the core stores: the worker asks the server what it says of the account when the app starts and when the account's page opens (`AccountSource.refresh`, `Core.accountRequest` / `accountRead`), and the map tab tells `SiteEditsModel.accountChanged` whenever the account changes, which counts `asked` up for the screens that show offers. A history's offers are the core's answer for the history as it was read (`Core.siteHistoryOffers`: undo, put back, bring back, report a revision, and its note), so a history opened by the site's identifier alone is answered, as after a removal. Who confirmed a site is read for the site (`siteConfirmationsOf`): the page says the core's sentence that nobody has yet only where the core has one for that kind of site, shows "Loading…" while the list is read and the reason with "Try again" where it cannot be, and the core's words under a list that is not whole. A write is sent with the session token as a report is; a refusal of adding or saving comes back as an answer (`SiteSent`), with the site in the way where one stands there. When someone else changed the site meanwhile (`siteWasChanged`), the draft is carried onto the site as it stands by the core's merge (`siteDraftRebased`, in `SiteDraft`), which needs the site the draft was made from; the form shows the core's words, what the others changed, the core's sentence at each field both changed (`clashesInWords`, where a fault's sentence stands) and offers "Show how it stands now". **"Removed lately"** (`SitesRemovedView.svelte`, a sheet opened from the foot of the sites' filter, offered to whoever is signed in) lists the removed sites of the two tiers in the core's lines (`Core.sitesRemoved`, a tier per request and none per site; the worker reads the pages and puts the one removed last first), the partners' first and the places from pilots under their layer's name, those only while their switch is on. A line the core says may be brought back (`mayBringBack`) has its entry: the site's history is read then for `bringBackRevision`, the core's question is asked, and the site's page opens. The server lets a browser keep a list of sites for an hour, so after a write the page lays the written site over the list it holds (`SitesModel.put`, `drop`) and the worker asks for lists past the browser's cache until it is closed (`SitesSource.wrote`); a page loaded anew within the hour can still be handed the old list. The place of a site is chosen by moving the map under a mark (`placing` on `OverviewMap.svelte`, `middle()`), which is what the core's words for it say.
- **The places from pilots are on the map and in the list only while their switch is on** ("Places from pilots", at the foot of `SitesFilterCard.svelte`): `SitesChoice.fromPilots`, off by default and kept with the filter in `localStorage`. It is the filter's `withPilots` (`asked` in `filter.ts`): the core chooses by it what the server is asked for (`sitesPathFor`, in the worker), says with it that a filter is on (`SitesFiltered.isOn`) and ends the filter's words with it, and the switch's own words are the choices' (`withPilotsWords`, `withPilotsAbout`). When it changes `SitesWatch.again` lets go of the answer held, which was for the other question. `SitesModel.put` does not lay a crowdsourced site over the map while the switch is off: after adding one the pilot sees its page, and the core's line says who sees it on the map. A crowdsourced site says its tier in the core's label (`fromPilots` in `src/lib/sites/words.ts`): under its name on the map and in the list, and on its page, where a partner's site says its own. The pack has no pin for the tier, so it has the pin of its use.
- **The pilot's own sites follow the account** (`Core.keptSitesSync`): the worker runs that sync after the logbook's in every `sync` and alone after a site was kept or forgotten (`AccountSource.syncKeptSites`), through `CoreSession.beginSync`, which stores each step as the logbook's run does. A browser that is not signed in asks nothing. `KeptSitesModel.synced` reads the list again for the core's note of where it is kept, and counts a change only when sites came from the account or went with it.
- **Continue with Google** (`src/lib/account/google.ts`, `GoogleHandleStep.svelte`; the worker's side in `src/lib/core/account-source.ts`) runs **no script of Google's**. Google Identity Services' button was tried first (2026-11-21) and broke under the content security policy: its script writes an inline `<style>` and `style` attributes, which the policy refuses, and allowing them by hash would break whenever Google changes its script. The app's own button (`GoogleButton.svelte`, the core's "Continue with Google") does Google's OpenID Connect redirect itself: it keeps a random `state` and `nonce` and what the pilot went for (sign in, link, delete) in `sessionStorage`, and goes to `https://accounts.google.com/o/oauth2/v2/auth` with the web client ID, `response_type=id_token`, `scope=openid email profile`, `prompt=select_account` and `redirect_uri=<origin>/settings/account/` (with the slash; the URIs registered on the web client are exactly these). The account page takes the answer out of the address bar at once (`history.replaceState`), checks the `state` and the token's `nonce` claim, and hands the token to the account model (`finishGoogle`). A token without the nonce is let through only when its `aud` is the development mode's made-up client (`venti-development.apps.googleusercontent.com`), which no other server takes: the development server's `GET /v1/dev/google-id-token` makes no nonce. A navigation needs no entry in the policy, so it names nothing of Google's. The handle and password form stands behind the core's "Sign in with a handle and password"; whether it was opened is kept in `localStorage` (`venti.account-with-password`). The web client ID is in `google.ts`; another build names its own with `VITE_GOOGLE_CLIENT_ID`. **The browser tests never reach Google**: every test opens the password form by that `localStorage` key (`e2e/helpers.ts`), and `e2e/google.spec.ts` answers Google's page with a redirect back carrying a development token (`e2e/made-up-google.ts`).
- **The "Continue with Google" button is drawn to Google's guidelines, not the design language's** (`src/lib/account/GoogleButton.svelte`; the sign-in form and the delete dialog). It is the one place in the app whose colours and sizes are Google's and not the pack's tokens, by the owner's word of 2026-11-21. From Google's "Sign in with Google branding guidelines" (<https://developers.google.com/identity/branding-guidelines>, read 2026-11-21), for a button an app draws itself: Light is fill `#FFFFFF`, a 1 px stroke inside `#747775`, words `#1F1F1F`; Dark is fill `#131314`, stroke `#8E918F`, words `#E3E3E3`; 40 high, a pill (the page's other shape is a rectangle with corners of 4); 12 before the logo, the logo 20 by 20, 10 after it, 12 after the words; the words at 14/20. Light shows on the light theme and Dark on the dark one (`prefers-color-scheme`). The sizes are in rem: the button grows whole with the reader's text size, which the guidelines allow as long as its proportions stay. **The typeface is the app's Fira Sans Medium, not the guidelines' Google Sans Medium** ("The button font is Google Sans Medium"): the app has no file of Google Sans and takes no font from another host; bundling it would be a new font with a licence to check, the owner's to decide. The page says nothing of hover, pressed or disabled, so those are the app's own (dimmed when pressed or disabled) and add no colour.
- **The Google "G"** is `src/lib/account/google-g.png`: Google's own file, <https://developers.google.com/static/identity/images/g-logo.png>, the logo as the guidelines page shows it under "Google logo in the 'Sign in with Google' button", fetched 2026-11-21 and not changed by a byte (200 by 204, SHA-256 `d1ce9c2af0b10a7333abc99bc706f9a6a199e5b65bf3e3009624f076b8638e6a`). It is Google's trademark, used under those guidelines: never redraw, recolour, crop or stretch it, and replace it only with a newer file of Google's. It is the gradient "G" of today's page, not the older one of four flat colours. It is a PNG because Google gives no vector file of the logo alone: the SVG buttons of its bundle (<https://developers.google.com/static/identity/images/signin-assets.zip>) draw the "G" with a `foreignObject` holding a `div` whose `style` attribute is a conic gradient, under blurs and a mask, which is not a drawing a browser shows the same everywhere as an image, and taking the logo out of a button would be redrawing it. At ten times the size it is shown, the PNG is sharp on every screen.
- **A token's secret is held by one page, in memory** (`src/routes/settings/account/programs/+page.svelte`): it comes from the worker in the answer to `giveAccess`, is shown by `TokenSecret.svelte` and let go of when the pilot says it is copied or the page is left. No model keeps it, and the page has no saved state. Until then `beforeNavigate` holds the app's other pages back.
- **Only what a page calls is bound.** What `wasm-bindgen` exports stays in the module. `Terrain::add_archive` and the list of a pilot's groups alone are not bound, because nothing in the app calls them.

## Hosts the app talks to

- The base map comes from OpenFreeMap and terrain from Mapterhorn ([docs/architecture.md](../../docs/architecture.md#maps-and-terrain) has the terms). Opening a flight also asks Mapterhorn for the elevation tiles under it: up to three dozen tiles of about 140 kB each for a flight of some tens of kilometres, coarser ones for a longer flight.
- The core's worker fetches those elevation tiles from the host in `src/lib/map/online.ts`, which the map uses too. That host is in the page's content security policy (`src/lib/app/security-policy.ts`) and in the web server's header for the workers (`deploy/Caddyfile`). Another host would need both. The browser tests fail on anything the policy refuses (`refused` in `e2e/helpers.ts`), which is how a missing entry shows.
- **The aerial view** is the layers of `map/style.json` marked `venti:view: aerial`, shown in place of those marked `drawn` (`setAerial` in `src/lib/map/setup.ts`); the style keeps them hidden, so nothing is asked of the photographs' providers until a pilot presses the layers button. Their hosts are in `online.ts` for the page's policy, and a unit test holds that list to the style's addresses. At a phone's width a short line under the map names the makers of the photographs that can show where the map has come to rest, worked out by `photosCredit` in `src/lib/map/aerial-credit.ts` from each aerial layer's `venti:credit`, its source's `bounds` and its `minzoom`; the providers' full wording is MapLibre's credits control, which names every aerial source whose layer shows at the zoom, wherever its photographs are. The page fetches the photographs itself, not a worker, so the web server's header for the workers does not name them (checked by hand with that header on 2026-11-20). In the browser tests every photograph is one square of green (`e2e/bundled-map.ts`): they show that the map asks and where it lays the answer, not what Bavaria looks like. For a look at the real thing, run the built site with the network on.
- **The flight in the air** is one MapLibre custom layer (`src/lib/flight/AirLayer.ts`, `renderingMode: '3d'`), added while the flight map is in 3D. Its geometry is built once, by the pure functions of `src/lib/flight/air.ts` (tested in `air.test.ts`), in a local frame of metres around the flight's first position; the layer multiplies `defaultProjectionData.mainMatrix` (Mercator 0 to 1) by the frame's matrix and only sets that and the ribbon's width, in pixels turned into metres at the current zoom, each frame. `modelViewProjectionMatrix` is not for Mercator coordinates in MapLibre 6: it drew everything far off screen. The words in the air and the marked moment's dot are elements the layer moves after each frame. `globalThis.ventiAir.stats` (frames drawn, the last frame's cost, vertices) is what `e2e/air.spec.ts` reads.
- **Thermals in a browser test.** The recorded forecasts are of a November day (the runs of 06:00 UTC on 21 November 2026, recorded at 09:25 UTC: ICON-D2's 48 hours, ICON-EU's 78, to noon of the 24th), with little or nothing to climb in. A test of a strong day answers `**/v1/forecast**` with `e2e/made-up-summer.ts`, a made-up day with the air of the core's own big-day test, and says so in a comment; never present its figures as a forecast. The recorded `crates/server/tests/golden/forecast.json` is read by `src/lib/core/forecast-source.test.ts`: when the server's recording is made again, that test's run, hour and wind change with it.
- **The thermal map in a browser test.** The development server's map is four recorded November days of four squares (the 21st and 22nd ICON-D2's, the 23rd and the 24th, not whole, ICON-EU's), nothing to climb in. `playwright.config.ts` starts `tools/made-up-day/serve.py` in front of it (port 8081, or `VENTI_MADE_UP_DAY_SERVER`; one already running is used), and `e2e/thermal-map.spec.ts` answers `**/v1/thermals` with that stand-in's made-up map, which has every kind of day, on four days (the third and fourth ICON-EU's, the fourth not whole), and `**/v1/forecast**` with the stand-in's made-up forecast of the same days. Its screenshots show a made-up map. Choose its days by their place, not their name: which one is today hangs on the browser's time zone as well as on the server's clock.
- **The rain radar in a browser test.** The development server has a recording of both sources of the first region, made within minutes of each other on 21 November 2026, and its radar's clock stands at 13:19 UTC: DWD's frames of 13:10 and 13:15, GeoSphere Austria's analysis of 12:45 and 13:00. The card's strip has the two stops of the radars, and both have the analysis of 13:00 under them: "Rain radar, 14:15, 4 minutes ago. Austria's analysis is of 14:00." on the tests' Berlin clock. The worker tells the core the moment by the server's clock, which in the development mode stands three days earlier, so the core counts the ages from the moment the list was answered at; that is why a test sees "4 minutes ago" whatever the day it runs on. `e2e/radar.spec.ts` and `src/lib/core/radar-source.test.ts` read which frames there are from the list itself and look at a line's form, so a new recording needs no new figures in them. The browser test shows old rain by answering `**/v1/radar` with the recorded list and a later `time`, and a server without a radar with a made-up `501`, and says so as made up. A frame's picture reaches the map as a `data:` address (`pictureAddress` in `src/lib/radar/radar.ts`), which the page's policy already lets the map fetch (`connect-src data:`): a `blob:` address would need a new entry. Which of the radar's layers the map draws, the lowest first, is in `globalThis.ventiRadar` (`radar-0` the analysis, `radar-1` the radars: a layer's place in the core's list), set by `OverviewMap.svelte`. A picture that lies under another at a moment is coloured clear wherever the one above sees the place (`radarFrameImageUnder`): the page names the frames above by their paths (`Drawn.above`) and keeps a coloured picture by its frame and those above it (`pictureKey`), since the same analysis lies under another radar frame at every moment; the worker keeps each frame's picture as the server sent it (`RadarSource`), so a frame is still fetched once, which the browser test counts. Whether a picture has loaded the map does not say: the card names a moment only once its pictures were handed to the map, and the screenshots show them. The radars see the region's north-west only, so a screenshot that is to show both layers is zoomed out to the whole region, where the test's map is blank.
- **Others in the air in a browser test** (`e2e/others.spec.ts`). The development server lists made-up aircraft of the Open Glider Network over the Tegernsee, a paraglider right by the Wallberg among them, but its network connects nowhere and says `connected: false`. The map draws a network's aircraft whatever `connected` says, since the server lists only what it heard in the last ten minutes, so the test takes the server's answer as it is. The worker asks for them with Venti's own pilots (`LiveSource.gliders`) and reads both answers with the core's `liveLayer`, whose `countWords` and `credits` the map shows as they are; what the map draws of them is in `globalThis.ventiOthers` (their identifiers), set by `OverviewMap.svelte`.
- **The map tab has four chips, two round buttons and one sheet** (the owner, 2026-11-21: plainer default screens). The chips are Forecast, Radar, Wind and Sites; the buttons "Layers" and "Show my position" (and the zoom pair on a wide screen). Everything else is `src/lib/map/MapLayersSheet.svelte`, opened by "Layers" in a `MapPanel` (a sheet at a phone's width, a card at the map's side on a wide screen): every layer as a row with a switch, the chips' four in the same state, and under the core's heading "Lists and plans" the rows that open the lists and the planner ("Wind stations", "Flying sites", "In the air", "Plan a route", the core's entry for adding a place). The sites' filter has no button of its own: it is inside the list of the sites (the row that unfolds `SitesFilterCard`, there even when the list is empty), and while a filter is on its line over the map still opens the pane. A new layer or tool is a row of the sheet (`layerRows`, `toolRows` in `src/routes/map/+page.svelte`), never a new chip or button. In a browser test: `openLayers`, `closeLayers`, `layerSwitch`, `switchLayer`, `toolRow`, `mapTool` and `openSitesFilter` in `e2e/helpers.ts`; `mapTabDrawn` waits for `.screen[data-wind]`, which the page sets with the wind's first answer.
- **The map tab's credits are closed from the start**, at every width: `createMap` is given `oncredits` there, which makes MapLibre's control compact and tells the page when its "i" (accessible name "Credits", by the map's `locale`) unfolds or folds it; the page shows Venti's credits (`.credits`) only while it is unfolded, every one complete. MapLibre folds its control again when the map is dragged, and Venti's fold with it. A test that reads a credit calls `openCredits(page)` first. A flight's map is as before: written out on a wide screen.
- **Climbs now, where thermals have been, and who flies at a site** (`src/lib/core/air-source.ts` in the worker; `src/lib/air/` on the page: `model.svelte.ts` asks, `on-map.ts` draws). Two rows of the layers' sheet, off until switched on and kept in `localStorage` (`venti.map-climbs`, `venti.map-flown`). The climbs are asked for the part in view and again every 30 s; a click on one opens the place's card with the core's `line`. The thermals are asked for every month and all hours (the core's `mapLayersWords` says so: the layer is not to be empty in winter), with the core's `note` under the row, its `terms` behind the link the core titles, and its words over the map where it shows too much or has no cell. The sheet's title, its two headings, the two layers' names and lines and the day alarm's name in the alarm form are `mapLayersWords()`. A site's page says the core's `siteAirWords` under the site's line, with no name for a site its source does not name. What the map draws of the two is in `globalThis.ventiAirLayers` (the climbs' labels, the number of cells, and where a mark stands on the screen). The development server's made-up gliders climb east of the Wallberg (+2.4 m/s) and south of the Tegernsee, and it has two cells of flown thermals above the valley: `e2e/air-layers.spec.ts` switches the wind, the sites and the pilots off so that a click finds the layer's own marks.
- **Lines over photographs.** A plain dark line the app adds to a map goes through `addLine` in `src/lib/map/casing.ts`, which puts a light casing under the lines listed in `CASED`; `setAerial` shows the casings with the photographs and hides them with the drawn map. A new dark line that should stand out over photographs is added to `CASED` and to its test.
- Flying plans are asked of the app's own origin by the worker, with the session token, through `sendToThisOrigin` in `src/lib/core/account-source.ts`. A new request from the pilot's account goes the same way.

## Testing

- **Tests of a module sit beside it** as `*.test.ts`. The browser tests are in `e2e/`.
- **The ground under a flight** is tested with real elevation tiles, cut one at a time from `apps/ios/Venti/Resources/MapDemo/terrain.pmtiles`: in Node by `src/lib/core/terrain-source.test.ts`, in the browser tests by `e2e/bundled-map.ts`, which answers every request to the tile hosts, the core's worker's among them. The 4 MB file is read where it lies; do not copy it into the app. The sample flight lies on two tiles of zoom 12; a flight outside the Tegernsee valley has no ground in the tests, and outside that valley the test maps are blank. That is the region's edge, not a fault.
- **`addSampleFlight` waits for the ground** (`groundDrawn` in `e2e/helpers.ts`). A test that keeps the elevation tiles away has to open the flight itself, as the last test of `e2e/ground.spec.ts` does.
- **With the ground, the marked moment of a flight reads "Over ground"; without it, "In the air".** A test that reads the flight panel at a moment says which of the two it expects, or reads the time.
- **The sites' filter is the core's** (`sitesFilterChoices`, `filterSites`, through the worker): which sites fit, which stand apart and every word about it. `src/lib/sites/filter.ts` holds only the pilot's choice and what is drawn while the answer is on its way; `SitesModel.refilter` asks whenever the sites or the filter change. "Forecast now" is not offered: the page has no forecast for the map's middle at hand. "Measured now" is the direction of the station nearest to the map's middle that is not old.
- **What the map tab drew of the sites** is in `globalThis.ventiSites` (the identifiers of the signs, of the muted signs and of the outlines), set by `OverviewMap.svelte` with the map's data, because a map cannot be asked what it draws; `e2e/sites.spec.ts` reads it. The counts of a filter differ between a phone's width and a desktop's, since the sites held are those of the part of the map asked for: a test reads the numbers from the core's line and checks the map and the list against them.
- **A station's air and past days in a browser test.** At the development server's clock it is dark, so none of its six stations gives a cloud base; Innsbruck/Universitaet and the Patscherkofel give the temperature step. Its stations have readings of the 18th only, so `e2e/wind.spec.ts` shows a drawn past day by answering the question for the 17th with the 18th's readings moved back a day, and says so as made up.
- **The development server's clock stands still** at 19:05 UTC on 18 November 2026, and its made-up plans are for the 18th to the 20th. The board of plans is asked for from the browser's own today. A test that wants a plan on the board posts one, or sets the browser's clock to that day with `page.clock.setFixedTime`; `e2e/plans.spec.ts` does both.
- **The two tiers of sites in a browser test** (`e2e/site-edit.spec.ts`). The development server has four made-up sites near Garmisch (10.85 to 10.95 east, 47.25 to 47.32 north), where the test map is blank: a partner's take-off with two confirmations (`venti:…s001`, Musterkogel West), a crowdsourced take-off with one (`venti-pilots:…s002`, Beispieljoch), a partner's landing and a crowdsourced site that was removed (`venti-pilots:…s004`, Musterkogel, which stands under "Removed lately" and which no test brings back: the same test at another width would not find it removed, so the test of "Removed lately" removes a place of its own and brings that one back). The last test of the file is the two tiers on a narrow phone with large text: the phone projects only, at 360 px wide with the root font at 130 % (set on the document after it loaded), with a check that nothing in an open sheet is drawn wider than the screen, and the list of confirmations while it is read, when it cannot be had (the request is held and then let fail with `context.route`) and after "Try again". Its demo account is that mode's one partner; an account a test makes is an ordinary pilot. No two sites of a tier may stand within 20 m of each other, and the same test runs at several widths on one server: a test that adds a site stands at a place of its own, drawn by chance south of the made-up ones, and removes the site again. The pilot's position is how a test says where: "Show my position" brings it to the map's middle, where the mark of the entry stands. A confirmation is for a day that is not after the server's today, and the development server's clock stands still, so the test that confirms sets the browser's clock to it (`page.clock.setFixedTime`). The partner's test corrects the one made-up crowdsourced site, which the same test does at other widths at the same time: it sends again when the core says someone else was quicker.
- **Tests that change groups make accounts of their own**, and the long one a group of its own. The demo account is only read.
- **The same test runs at four widths, more than one at a time, on one server.** What one run posts into the development mode's "Mustergruppe", the other sees for a moment. Look for a made-up plan by its place in full, and for a member by name.
- **Members who came into a group at the same moment are listed in an order no test can know.** With the server's clock standing still, that is every two members a test adds.
- **A plan with a position cannot be made in the web app**, which has no waypoints to take one from. `postFromAPhone` in `e2e/plans.spec.ts` posts one through the API.
- **A day of a plan is a date, not a moment.** Unit tests of `src/lib/groups/days.ts` set the time zone of the test process (`process.env.TZ`) to show that today is the reader's date and not UTC's; they put it back afterwards.
- **The screenshots show the test machine's typeface**, because the app uses the system's. A bare Linux machine's is wide and cuts short text that fits on a phone; `e2e/fonts.conf` says how the `Web` workflow gives its screenshots Inter instead.

## Pitfalls

- **Colours, sizes and radii come from the design pack** (`design/tokens`), through the app's names in `src/app.css`. A screen writes none of its own: `#` colours and `rgb(…)` in a component are a mistake, except what the map engine needs as a value, which `src/lib/design/palette.ts` reads from `design/tokens/tokens.json`. Do not edit files under `design/`: they are the owner's.
- **Wide is denser, narrow is the phone app** (the owner, 2026-11-21; `docs/design.md`, Web, "On a large screen the layout is denser"). Do not build a wide screen by stretching the narrow one: wide means more on the screen at once, things side by side, tables with columns and sortable headings where there are rows, the pack's label size (14 px) as body text and controls about 32 px high. Cards, sheets, the tab bar and 48 px targets are for narrow. It stays a website in Venti's look: nothing of macOS is imitated (no window toolbar, no file-browser sidebar, no right-click menus), which the owner said in so many words after an earlier wording here asked for it. A new screen is designed for both widths from the start and its browser tests keep screenshots of both.
- **Links are the pack's link colour (`--link`), the chosen control and the main button its primary (`--accent`)**, and the focus ring `--color-focus`. The pack's coral (`--color-accent`) is for the one action that starts or records a flight, which the web has none of; the selected section's icon in the navigation is its coral text colour, as in the pack's tab bar.

- **A number reaches the page through `src/lib/design/format.ts`**, which writes it the English way whatever the reader's region. `toLocaleString` and an `Intl.NumberFormat` of the reader's locale write "2,5 km" beside the core's "10.0 km NE" for a reader in Germany.
- **A form that fills itself when it opens must not fill itself again** while the pilot types. The board is asked for anew when the tab comes back to the front, which hands the form new objects. `src/lib/groups/PlanForm.svelte` reads what it starts from inside `untrack`, so that only opening fills it.
- **A board is one account's.** `src/lib/groups/board.ts` puts the board away when another pilot has signed in, before the server is asked. State of that kind that outlives a page needs the same.
- **What a pilot typed is set as text.** No `{@html}` for a group's name, a place or a note. `e2e/plans.spec.ts` posts a plan whose place is markup and looks for no image.
- **A dialog stays in the page and is opened and closed**, as on the other screens, and keeps its words while it closes. _To verify:_ what a browser does with the focus when an open dialog is taken out of the page instead; it was not tried.
- **A button inside a `group-card` that is not a row of it** gets the card's hairline over it (`.group-card > * + *`): give it `box-shadow: none`, as the refusal in `SiteEditForm.svelte` does.
- **The switch in a row** is the class `toggle` in `src/app.css`. It is not a style of one screen.
- **The navigation** (`src/lib/app/Navigation.svelte`) is the pack's tab bar along the bottom below 56rem (896 px) with six sections (Home, Map, Today, Logbook, Plans, Settings), sharing a phone's width; a seventh needs the bar looked at at 360 px. From 56rem it is a website's bar across the top (`--nav-top` high, sticky): the logo lockup, Home, Map, Today, Flights, Ranking, Logbook, Plans as words, and Settings and the account at the right. Between a phone and 896 px the phone's layout holds. A page that fills the window is `calc(100dvh - var(--nav-top))` high, never `100dvh`.
- **A wide page is a `.desk`** (`src/app.css`): a centred column of at most `--content-max` (1440 px), a `.page-head` with the title and the page's actions on one row, and `.columns` of twelve that panels span with `.span-3` to `.span-12`; below 56rem it is the phone's column and the panels stand one under the other. The home page, the wide `/plans`, everyone's flights, the ranking, a pilot's and a place's page, Today and the settings use it: a data page has the whole width on a wide screen, never a narrow column of its own. The map and a flight's screen are full-bleed under the bar; a flight's has the map at the left two thirds, the altitude profile under it (`FlightChart.svelte`) and the numbers and details in a column at the right. The settings' `+layout.svelte` puts the sections (General, Account, Airspace) in a list at the left of a wide screen, so a test that clicks a settings row names it inside `.settings-page`, where the list is not. Tables of flights keep their heading in view with `position: sticky` under the bar, inside a card clipped with `overflow: clip` (not `hidden`, which would make the card the heading's scroller).
- **The home page is `/` and the map `/map`.** `mapHref` makes every link to the map; `/?lat=…&lon=…`, the map's old address, is sent on to `/map/?…` by the home page. `?show=pilots` opens the map with the Pilots layer on whatever the browser remembers. The home's panels are `src/lib/home/` (`HomeModel` asks for each on its own; Today's take-offs are `App.today`'s, the alarms `App.alerts`'); every word about a verdict or a count is the core's, the panels' titles are the page's.

## Where the session token is kept

[docs/architecture.md](../../docs/architecture.md#the-account-in-the-browser) says where: in IndexedDB, read by the worker only. What was weighed:

- **What that is good for.** The browser sends the token nowhere by itself, as it would a cookie, so no other site can make the browser act for the pilot. It lasts across visits and is shared by the site's tabs, which a sync that runs by itself needs. It goes when the pilot signs out, when the server no longer takes it, and with the site's data.
- **What it does not protect against.** A script running on this origin could read the token and act for the account until that session is signed out: read, upload, share and delete flights. It could not delete the account or change the password, which need the password. The app loads no script from anywhere else: no analytics, no fonts, no content network, and the map engine is part of the build. What remains is a flaw in the app or in a package it is built from that lets a stranger's script run, and whoever can change the files on the web server. Against the first there is the content security policy below.
- **Why not elsewhere.** `localStorage` is as readable and cannot be reached from the worker. `sessionStorage` or memory alone would sign the pilot out with every closed tab, with a password of fifteen characters and a sync that is meant to run by itself.

The better place is a cookie that scripts cannot read (`HttpOnly`). The server sets no cookies today; the decision log in `docs/architecture.md` lists what it would have to offer.

## The content security policy

Why it is a `meta` element written by SvelteKit's `csp` setting (`vite.config.ts`, over the list in `src/lib/app/security-policy.ts`), and why the web server adds two headers, is in the decision log of [docs/architecture.md](../../docs/architecture.md#decision-log). The page's policy:

```
default-src 'none';
script-src 'self' 'sha256-…';
style-src 'self';
style-src-attr 'unsafe-hashes' 'sha256-…';
img-src 'self' data:;
connect-src 'self' data: https://tiles.openfreemap.org https://tiles.mapterhorn.com https://tiles.maps.eox.at https://wmts.geo.admin.ch https://geoservices.buergernetz.bz.it https://wmtsod1.bayernwolke.de https://thermal.kk7.ch;
font-src 'self';
manifest-src 'self';
worker-src 'self';
base-uri 'none';
form-action 'none'
```

| `font-src 'self'`                                                        | Fira Sans, the design pack's typeface, from the app's own files (`design/fonts`, taken in by the build through `design/tokens/tokens.css`). No font host.                                                                                                                                                                                                                                                                                                                      |

| `worker-src 'self'`                                                      | The core and the map engine each run in a worker, both from files of the app. `script-src` would say the same; it is said outright so that a change there cannot change it unseen.                                                                                                                                                                                                                                                                                             |
| `base-uri 'none'`, `form-action 'none'`                                  | No `base` element can send relative addresses elsewhere, and no form posts anywhere: the app's forms are handled by its scripts.                                                                                                                                                                                                                                                                                                                                               |

Not in it, because the browser refused nothing without them: `'unsafe-inline'`, `'unsafe-eval'`, `'wasm-unsafe-eval'` and `blob:`. The core's WebAssembly is compiled in its worker, which a page's policy does not reach, and the map engine is given its worker as a file of the app (`setWorkerUrl`) and makes none from a blob.

**How the list was found and is kept true.** By starting from `default-src 'none'` with `'self'` alone for scripts, styles, images, connections and workers, reading what Chromium refused while the screens were used, then running the browser tests in all four projects (2026-11-19). The tests now fail on anything the browser refuses under the policy, in a page or in a worker, so a change that needs a new entry shows itself. `e2e/policy.spec.ts` checks that every page has the policy ahead of everything it loads, and that an inline script, a handler in markup, text made into code and a request to another host are refused. A test in `e2e/sites.spec.ts` names a site in Arabic, Thai and Georgian, which is what `connect-src data:` is for. Signing in with Google is a navigation to Google's page and back, which the policy does not govern (`form-action` is about forms; no browser enforces `navigate-to`). Who is in the air, everyone's flights, flying plans and the ground under a flight needed no new entry: they are fetched from the app's own origin or from `tiles.mapterhorn.com`, and links to the server's pages are not governed by the policy.

**What the web server sends** (`deploy/Caddyfile`). A page cannot say who may frame it (browsers ignore `frame-ancestors` in a `meta` element), so Caddy sends `Content-Security-Policy: frame-ancestors 'none'; base-uri 'none'` and `X-Frame-Options: DENY` with the app's pages. A worker is held to the policy that arrives with its own script, not to its page's ([CSP3](https://www.w3.org/TR/CSP3/); MDN, "CSP in workers"), so Caddy sends this with every script file of the app, because the build decides where the two workers' scripts are (today `/_app/immutable/workers/` and `/_app/immutable/assets/`):

```
Content-Security-Policy: default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self' https://tiles.openfreemap.org https://tiles.mapterhorn.com
```

CI compares its tile hosts with those in `src/lib/map/online.ts`; when the tile hosts change, both change. It was tried in Chromium twice: with a proxy in the browser tests that added the header to the core's worker (every screen worked; without `'wasm-unsafe-eval'` the core did not start), and through the real Caddy (without the tile hosts the map engine's worker fetched no tile).

_To verify:_ all of this was seen in Chromium only. A browser that holds a worker to its page's policy would need `'wasm-unsafe-eval'` in the page's `script-src`, or the core does not start. Where a browser lacks `createImageBitmap`, the map engine decodes elevation tiles through an image with a `blob:` address, which would need `blob:` in `img-src`.

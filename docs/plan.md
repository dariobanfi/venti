# Product plan

Last revised: 2026-11-22

## Goal

Paragliding pilots use one app to check conditions, another to plan, another as flight computer, another to publish flights, and chat groups to organise flying days. None of them share data. This project puts those jobs into one free app with one community, so that a flight is planned, flown, analysed and shared in the same place.

## Owner decisions

These were set by the owner on 2026-11-18, and later where a date says so, and are not open for re-litigation in later sessions.

1. **Free and open source.** No monetisation planned. Sponsorship may come later.
2. **The project does not pay for AI.** Users connect their own assistant or credentials.
3. **Native UI on every platform.** SwiftUI on iOS, Jetpack Compose on Android, a real web app in the browser. No React Native, no Flutter, no web views inside the mobile apps.
4. **One Rust codebase** below the UI, shared by all clients and the server.
5. **One central platform, self-hosted on one Linux server** the owner pays for, and on a set of them when it grows. No services that bill by usage. Venti is not made for clubs or pilots to run a server of their own: there is one Venti. The server's address is built into the apps and is no setting (the owner, 2026-11-21: "The server should be baked into the app, it should not be an optional setting"). The web app is served by the server and asks where it came from. Each phone app takes the address from its build: until Venti has a public address, a debug build asks the owner's own Venti on the Mac it was built on (as an emulator or a simulator reaches it) and a release build cannot be made; with the public address known, it is one line in each app's build. The apps say "Venti" and never "your Venti server", and they have no state for a server that was not set: only for one that is not reached. Built in both phone apps on 2026-11-21.
6. **Every external data source sits behind an adapter.** Regions are configuration. See [data-sources.md](data-sources.md).
7. **First region: Germany and Austria**, then the whole Alps. The owner is based in Munich.
8. **iOS first.** The owner flies with an iPhone and an external Bluetooth vario.
9. **XCTrack is the benchmark for the cockpit.** See [xctrack-parity.md](xctrack-parity.md).
10. **Best available open maps, with very good terrain depiction.**
11. **AI sessions write and maintain all code.** The repository must stay understandable to a session that has never seen it.
12. **The app is called Venti** and is licensed under AGPL-3.0-or-later.
13. **It must be able to carry many users.** The server design starts on one machine and must be able to grow beyond it.
14. **The server is a data platform first** (the owner, 2026-11-21: "when building the server, you have to think about it as a data platform first, because we want this server to become the center point of paragliding, and people can use it to create takeoffs, track their flights, any … kind of community data. It will become the central hub for it in the future. … So it needs to be very open and supporting of that, and allow people to put their data in there and query it."). The apps are one client of it among those to come. What follows for every piece of server work: what pilots make (flights, take-offs and what they know of them, plans, whatever comes next) is stored as data with its author, its time, where it came from and the licence it is given under, not as a screen's state; everything that is read can be asked for through the documented API by anyone it is open to, in ways a program can use (by place, by time, by pilot, in bulk), and what a pilot may write an app of another maker may write for them with their leave; the data of others' sources stays apart from the community's own, each under its licence, so that the community's can be handed out freely. Where a feature could live on the device alone or on the server, it belongs on the server unless it is the pilot's private matter, and then it is theirs to move there. What pilots give as flying sites is given under CC0 1.0 (the owner, 2026-11-21, asked under which licence pilots give their take-offs to Venti: "CC0, public domain"). What this asks of the server as it stands is in [data-platform.md](data-platform.md): the principles a new endpoint or table is judged by, what the server holds and every way in and out of it, a design for take-offs that pilots make, and the missing pieces in the order to build them. **Who adds a take-off** (the owner, later on 2026-11-21, after the three apps had been given a form for any signed-in pilot to add and correct a site): "pilots shouldn't be able to add the [take-offs] from the app. … the [take-offs] usually are … really official, and they don't change so much. But … the backend, and … the website, so not the app, should support adding new ones for … trusted partners and so on." So: the phone apps read the sites and add or change none; the server and the web app take a site from an account the owner has named as trusted, and from a program holding such an account's token; any pilot can still report a site. The form in the two phone apps is taken out again, and the web's is shown to a trusted account alone. **And a crowdsourced layer beside it** (the owner, a little later the same day): "maybe don't take it all out, but let it be kind of like a crowdsourced feature, which is less official. It's not maybe displayed by default, but is something like crowdsourced, where someone can say, yes, I started here and it was good." So there are two layers of Venti's own, and this replaces the sentence before where they differ: the partners' sites (`venti`), written by trusted accounts and shown by default; and the crowdsourced sites (`venti-pilots`), which any signed-in pilot adds and corrects from the three apps, which no map shows until its pilot switches them on, and which are marked as from pilots. On a site of either layer a pilot can say "I took off here and it was good". The form stays in the three apps and adds to the crowdsourced layer; a trusted account's form adds to the partners'. Built on the server and in part in the core on 2026-11-21 ([what stands](data-platform.md#what-stands-of-it-2026-11-21)).
15. **Advanced features stay out of the way** (the owner, 2026-11-22: "Don't exaggerate with crazy niche features in general, I still want to keep this user friedly. Advanced features should either be seamless or be available from a specific view or toggle able with a setting"). What follows: an advanced feature reaches a screen in one of three ways only: seamless, with no control of its own (a reading that appears when it has something to say); as a view the pilot opens on purpose; or behind a setting that is off by default. Never as a new control on a default screen. Built so already: the glider's polar is unset until a pilot sets one (`f9e8968`), and the places from pilots stay off the map until a pilot switches them on. [design.md](design.md) applies it to the screens of the live air, of the cockpit's readings and of the map's layers sheet, built on the apps the night of 2026-11-22.
16. **Everything is open through the API and the connector, except flights their pilot keeps private** (the owner, 2026-11-22, asked whether a pilot's own assistant may read their private flights once the pilot agrees: "Yeah, of course. All the data should be available through an MCP server and through an API publicly, except flights that users keep private."). What follows: what Venti holds and may hand out is readable without an account through the documented API and through the connector (MCP), within the bounds and the licences of its sources. A flight its pilot keeps private, or shares by link, is in no public answer; it is read only by the pilot, and by an app or an assistant the pilot has agreed to on Venti's own consent page, with a token limited to what was agreed, which the pilot can withdraw. This settles the question that stood before the authorization server ([data-platform.md](data-platform.md#what-is-missing-in-build-order), piece 12).
17. **Venti is not commercial, and a licence that is stated is enough** (the owner, 2026-11-22, after a provider was marked "must be asked" before its photographs could be packed into a region's file: "remember, what we are building is not commercial, so you don't have to ask this permission if the things are marked."). What follows: Venti is free, open source and earns nothing, so a source whose own pages state a licence that allows what Venti does, also one that allows it only for non-commercial use, is used under that licence without asking its provider first. "Ask" stays for a source that states no licence or terms for the use, or whose stated terms do not cover it; a licence's other conditions (credit, share-alike, no mixing of licence families in one record or file) hold as before. As read by the session, for the owner to correct: a non-commercial licence binds whoever takes Venti's code and runs it commercially, which the documents of each such source say; and it would have to be looked at again the day Venti takes money.
18. **Data plugs in and out, at every layer** (the owner, 2026-11-22, on hearing that each new station network is an adapter of its own: "Make sure that all data is easily pluggable in and out at multiple layers. I expect this to be open, and people want to maybe, you know, in some weird country, they have some useful data source that they would like to integrate in this app, and it needs to be flexible how to do that."). What follows: somebody who knows a useful source in their country can bring it into Venti without knowing the whole project, and whoever runs a server can take a source out again without code. So a source is one self-contained adapter behind one contract, with a written guide and a template to start from; which sources a region uses is configuration, not code; a map layer from a provider is an entry of data, not a change to three apps; and what Venti holds leaves it as easily, through the documented API, the connector and the dumps. Every new kind of data is judged by it: can a stranger add a second provider of it by following the guide. Built for station networks on 2026-11-22 (`a4153808`): the guide [adding-a-source.md](adding-a-source.md), the template `tools/new-source/template` and the check `tools/new-source/check.sh`; what cannot be plugged in that way yet is the guide's last section.

19. **Show, do not tell** (the owner, 2026-11-22, on the web map's rain radar panel: "what is that huge block of text? come on.. user doesn't need all of that text", and on the banner "Zoom in to see the gliders of the Open Glider Network.": "It's also not needed. Show, do not tell. I think people can figure it out themselves."). What follows: a screen gives the fewest words a pilot acts on, a line, a key, a number; no hint that explains the interface; an explanation goes behind an "i" or is cut; a panel never covers the map it belongs to; credits stand behind the map's credits button unless a licence asks for more; a "to verify" or any other caveat of the project's own is in `docs/` and never on a screen.
20. **The website holds flights online only** (the owner, 2026-11-22: "On the website there should be only online data. There is never a use case where someone creates or uploads a flight without an account on the website."). The web keeps no logbook of its own in the browser and has no sync; a pilot signs in to see or bring in flights. The phones keep their flights on the device, offline first, as before. This replaces the web's logbook in the browser (decision log, 2026-11-19 and 20).
21. **A pilot's flights are public unless the pilot keeps them private** (the owner, 2026-11-22, on finding their 101 flights missing from everyone's flights: "I thought they should be public"). This is how decision 16 reads: a new flight is public by the pilot's own setting, which is on until they switch it off, and a pilot can make all their flights public or private at once.
22. **Venti becomes the source of truth for flying sites** (the owner, 2026-11-22: "Important thing that at the end we store the data, because we will become the single source of truth"; on the DHV's site database: "you can do it, I got permissions"). Sites from every source Venti may use are stored, a place that several sources describe is shown once, and pilots' own records on Venti (CC0) grow into the reference. The licence rules above still hold: a share-alike source's fields are not copied into Venti's own records; its record is linked.
23. **The cockpit is the Fly tab, and an instrument first** (the owner, 2026-11-22: "by default it should open the flying view. The things you display now should be some settings that you can configure through a settings button somewhere, but not in the main view of the cockpit since real estate is really expensive in there"; "the thermal assistant also shows the wind direction and intensity"; "in the settings you should choose your device, and if you, let's say, choose the external vario first, the sound on the device is muted, but if for any reason the Bluetooth device disconnects, then you should pick up with the device sound"; "whenever the app is open, even if I'm in another section, whenever I start flying, it detects that I auto start flying, so it switches to the cockpit and starts the recording"; "make sure that the cockpit functionality really works well"). What follows: the Fly tab opens on the cockpit; what was checked before take-off is behind one settings button and speaks in the cockpit only when something is wrong; the thermal view beside the map is always there, with the wind's direction and strength; the climb comes from the external vario, else from the phone's pressure sensor, never from the satellite height alone; the phone sounds only while no external vario is connected, and only in flight; a take-off seen from any tab opens the cockpit and records; the recording must survive the screen going off, the app going to the back and the system's battery saving, and what has been shown to survive is written down with where it was shown.

## Modes

The app has five modes on web and phone. The cockpit is phone-only.

| Mode | Job |
|---|---|
| **Today** | What is flyable right now: live wind, webcams, who is in the air |
| **Plan** | Forecast and route planning for cross-country and hike & fly |
| **Fly** | Live cockpit and flight recorder |
| **Review** | Logbook, 3D replay, insights, comparison with other pilots |
| **Community** | Feed, groups, events, spontaneous flying days |

All modes read and write the same objects through one API: sites, wind stations, airspace, flights, pilots, live positions. The assistant uses that same API as its tools.

### Fly
The full checklist is in [xctrack-parity.md](xctrack-parity.md). XCTrack is Android-only and its developers state that they do not plan an iOS version, so an iPhone cockpit at that level does not exist today. The principles:
- The recorder runs as a native background service. A UI crash or phone call never costs the track.
- **The flight starts by itself** (asked for by the owner on 2026-11-20; on the iPhone since that day, and on Android too, as its code and unit tests showed when they were read on 2026-11-21: `FlySession.startFlight`, `recordNow`, `endByItself`). As XCTrack does it: the pilot opens the cockpit on the ground, and it is ready ("Ready for take-off"). It keeps the last half minute of positions and writes nothing; when the flight computer notices the take-off (4 m/s over the ground for 5 s, or 25 m of height steadily over half a minute), the recording begins from that half minute and live tracking starts; two minutes after the glider has come to rest the flight is saved to the logbook without a tap. Being ready costs battery, so the cockpit closes by itself after two hours without a take-off. "Record now" records at once. The rules are in the core (`core::cockpit`, `flight::live`); all of them are to verify in the air.
- Everything works offline: maps, terrain, airspace, sites and the last forecast are on the device.
- External Bluetooth varios are first-class, because phone barometers are too slow for a good vario.
- Safety-relevant warnings (airspace, terrain, landing options) are deterministic code. They never depend on a network connection or a language model.

### Review
- IGC upload and bulk import of existing flight history, with automatic scoring.
- **A pilot's XContest history, brought in** (the owner, 2026-11-20: "think of allowing import from XContest"; and earlier: Venti as a bridge, so that a pilot can use it while still posting to XContest). XContest publishes no way to read a pilot's flights, its flight pages ask for a sign-in and its `robots.txt` shuts them out ([data-sources.md](data-sources.md#leagues-a-flight-goes-to)), so Venti does not read XContest. It does not need to: every flight on XContest began as a file on the pilot's own device, and the pilot still has it.
  - *The files XCTrack keeps* are the whole history of most XContest pilots: one IGC file for every flight, in XCTrack's tracklog folder on the phone and in whatever backup the pilot keeps of it. The owner's 45 flights of four years came in from such a folder in 13 seconds on 2026-11-20, each read, analysed and scored. So the import is: point Venti at a folder once, and everything in it is in the logbook. A flight the logbook already has is recognised by its positions and not taken twice, so the same folder can be brought in again at any time.
  - *The bridge, built on Android on 2026-11-20:* the logbook's plus button has "Bring in new flights from a folder"; Venti keeps Android's permission to read the folder the pilot chose and looks into it whenever it comes to the front, bringing in the flight files that are new or changed (a file is known by where it lies, its size and when it changed; the core recognises a flight it has in any case). A pilot then flies with XCTrack as before, the flight is in Venti's logbook by itself, and from there it goes to a league with "Send to a league". *Where XCTrack keeps its tracklogs, to verify on a phone:* by what is known here, current XCTrack writes them to its own folder under `Android/data/org.xcontest.XCTrack/`, and since Android 11 the system's folder picker does not offer `Android/data` to another app at all; Venti cannot be given that folder, and no app can without broad storage rights, which Venti does not ask for. If so, the way is XCTrack's own setting for where tracklogs go (*to verify that it has one, and what it offers*), pointed at a folder both apps can see, such as one under Documents; or a copy the pilot keeps elsewhere (a cloud folder that the system's picker shows). Untried on the emulator, which has no XCTrack: the permission kept across a restart of the phone, a folder on a cloud provider, and a folder of thousands of flights.
  - *One flight at a time, from XContest itself:* a signed-in pilot can download a flight's file from its page and bring it in like any other (*to verify by the owner, who has an account*). Tedious for a whole history; right for the odd flight that is on no device any more.
  - *Asked of XContest, in the same letter as the upload interface:* a way for a pilot to fetch their own flights, or to export them all at once. A pilot in the EU may ask XContest for their own data in any case; an interface would spare both sides the letters.
  - *Not done:* signing in to XContest inside Venti and reading the pilot's pages with their session, or a script for the pilot's browser that does. Both read pages XContest has shut to programs, and both break whenever a page changes.
- 3D replay, with photos and videos pinned to the moment and place they were taken.
- Automatic breakdown of every thermal and glide, time spent climbing, gliding and searching, wind by altitude.
- Comparison with pilots in the same area that day: climb rate in the same thermals, where lines diverged and what that cost, lift flown past.
- Trends by season, wing and site.
- **Asked for by the owner on 2026-11-20, to do:** a pilot's flying in numbers and what it says about them. (1) Statistics of the flights done, beyond the totals, the months and the bests there are today: by site, by glider, by kind of route, by year against year. Built on 2026-11-21 in the core and shown on the iPhone: year against year, the months of the year over all years, the kinds of route, and the typical flight (the middle one of all); since the same day also on Android and the web. By take-off it is worked out in the core since that day (`site_statistics`: the places flights began at, by the pilot's own waypoint names where there are any) and shown on the iPhone, on Android and on the web; by glider there are the totals. (2) The same numbers beside those of the pilots around: the pilots who fly the same sites, the same days, the same class of glider, so that "my average climb" and "my longest flight" have something to stand against. (3) Learnings, tendencies and mistakes, worked out from the pilot's own tracks by the deterministic code that already breaks a flight into thermals and glides: which way they turn, how long they stay in a thermal that has weakened, how high they leave, what their glides cost against the pilots beside them, where flights ended and why, airspace come close to. Said as observations with the flights they are from, never as a verdict on the pilot, and never as advice about what is safe. Built in the core on 2026-11-21 and shown since the same day on the statistics' screen "How you fly" (seen running on all three, on the phones since 2026-11-21 in UI tests that fill the logbook with five copies of the made-up sample flight, as [design.md](design.md#logbook) says): each flight's figures (which way each thermal was circled, how measured thermals ended and the time after their top, height gained, the best thermal, glides of a kilometre) are counted on import and kept with the flight, and `tendencies` says over the whole logbook which way the pilot circles, how their thermals end, the time after the top, how they climb and glide, and the share of the airtime spent circling, each with a flight that shows it; rules and limits in [design.md](design.md#logbook). Since the same day also how far below a thermal's top the pilot leaves it, and where flights end against where they began (within a kilometre, and the farthest). To do: what their glides cost against the pilots beside them; why flights ended where they did (a landing field reached on purpose, or the ground reached first); airspace come close to; and every limit checked with pilots.
- **To do: a flight's times by the clock of the place it was flown at.** A flight's take-off, landing and replay times are shown by the clock of whoever reads them, which is right at home and wrong for a flight flown in another time zone, or looked at from one (found on 2026-11-20 by running real flights through the app). An IGC file says the time in UTC and rarely the zone. Showing the place's own time needs a table of the world's time zones by place and their rules in the core, a few megabytes in every app; the two open tables are timezone-boundary-builder's outlines (ODbL, from OpenStreetMap) and the IANA rules (public domain). To decide: whether that weight is worth it, or whether the page says "your clock" beside the times instead.

### Community
- Profiles, follows, a feed of flights with media, comments, share pages with rich previews.
- Groups with chat and a "flying today?" board, visible to the group or to pilots nearby.
- Events with local discovery; site pages anyone can improve.
- Privacy controls from the first release: private, followers-only or public flights, a hidden home zone, delayed or friends-only live tracking.
- Later: leagues, classic-route leaderboards, club pages. A first ranking exists since 2026-11-20 (the best three public flights of a year). **Asked for by the owner on 2026-11-20, to do:** leaderboards beyond it: by site (its records and its regulars), by kind of route, by class of glider, by region, and among the pilots a pilot follows or flies with.

### Assistant
Users bring their own AI; details are in [architecture.md](architecture.md#bring-your-own-ai).
- **Connector:** the server exposes its tools over MCP, so a pilot adds the app to their own Claude or ChatGPT and asks there ("how is the wind toward Innsbruck this afternoon?").
- **In-app assistant:** runs on the pilot's own API key or account, speaks and listens in flight, and can raise proactive alerts.
- **Flagship question:** "which valley gets me home tonight?" Reachable landings from the current height and wind, then nearest stops, then train and bus itineraries, ranked by arrival time and glide margin.

| Live tracking | **Open, four things**, all built one way for now ([architecture.md](architecture.md#live-tracks)). (1) A live track is kept for 48 hours after its last position and then removed, also from the backups; another number is one setting (`retention.live_hours`). (2) Every account may put its glider on everyone's map. While accounts are by invite that is the people the owner invited; with open registration one account can show 30 made-up gliders a day. Since 2026-11-20 a track can be reported, whoever runs the server can remove it, and an account can be kept off the map, all by hand and after the fact. (3) Positions are shown as they arrive. The plan promises "delayed or friends-only live tracking"; neither is built, and a delay would have to be weighed against what a live link is mostly for, which is someone at home knowing where the pilot is now. (4) A pilot's link shows the pilot's display name and handle to whoever has it, as a shared flight does. |
| Public flights | **Open, three things**, all built one way for now ([architecture.md](architecture.md#flights)). (1) The list of everyone's public flights can be ordered by points, and the points are the server's own, across every kind of route. Whether a ranking should be by kind of route, by glider class or by a league's rules is not decided. (2) A flight in the list has the coordinates of its take-off and no place name. The only names the server has are OpenStreetMap's flying sites, whose licence is share-alike; whether a site's name may stand beside a pilot's flight in one answer is a question about that licence, and the owner's. (3) Anyone can read the list without an account, as anyone can read a pilot's page. Since 2026-11-20 the server also ranks its pilots (`GET /v1/ranking`) and the web app shows it: the sum of a pilot's best three public flights, of any kind of route, in a calendar year by UTC or in all years. **How many flights count, what a season is, and whether gliders are ranked by class are the owner's to decide**; the number is one constant (`RANKING_COUNTED`) and the season is the client's span of time. |
| Reports and taking down | **Open, seven things**, all built one way for now ([architecture.md](architecture.md#reports-and-taking-down)). (1) The reasons a report can give are six: offensive, impersonation, privacy, not a flight, spam, other. There is none about how someone flew, such as airspace. (2) A report is kept until it is closed and for 90 days after, goes when the reporter's or the reported pilot's account is deleted, and is in the backups. (3) Whoever runs the server sees who reported; nobody else learns it, and the reported pilot is told nothing. (4) A pilot whose flight was taken down, or whose publishing was suspended, is told that and since when, and not why. The server has no way to write to a pilot, so a reason would have to stand on the flight. (5) Suspending an account's publishing turns its public flights and live tracks into ones shared by link; it hides nothing from those who have a link, and lifting it makes nothing public again. (6) Nothing acts by itself and nobody is notified: the server's log says once a day how many reports wait. Someone has to read them. | Groups and plans | **Open, twelve things**, all built one way for now, the plainest and most private each time ([architecture.md](architecture.md#groups-and-plans)). (1) A group is found by nobody: a pilot comes in with an invite code that the keeper hands out. The board "visible to pilots nearby" that the features above name is not built. (2) A group shows its members each other's handle and display name and the plans, and opens nothing else: no flight and no live track is seen by anyone because of a group. (3) A plan belongs to one group; for two groups it is posted twice. (4) A plan is kept for two days after its day and then removed, and it is not in the backups, so after a restore the plans for the days ahead have to be posted again; another number is one setting (`retention.plan_days`). (5) A group has one keeper, who renames it, makes a new invite code, removes a member, hands the keeping on, deletes the group and can delete any plan. The keeper cannot change another member's plan and sees nothing the members do not see, the code apart. (6) When the keeper leaves or deletes their account, the member who has been in the group longest keeps it; when the last member goes, the group is deleted. The group's name stays, also when the account that typed it is deleted. (7) What a pilot put into a group goes when they leave, are removed or delete their account: their plans, also for those who were in on them, and their word on the plans of others. (8) The invite code is shown to the keeper once and the server keeps no readable copy; a keeper who lost it makes a new one, which ends the old one. Removing a member ends the code too. There is no invite link. (9) A plan's day is a date on the calendar of the place, without a time zone. Where the server has to know which day is today it goes by the date in UTC: it takes a plan for the day before that date too, which west of Greenwich is not over, and a list that names no first day begins at that date. (10) A plan's place is what the pilot types, with a position if they mark one; nothing of the flying sites the server collects goes into a plan, because those are OpenStreetMap's under a share-alike licence. Whether a client may offer a site's name to type in is the question the row "Public flights" already asks. (11) The limits: an account is in 20 groups, a group has 50 members and 100 plans at a time; an account makes 10 groups, tries 20 invite codes and posts or changes 50 plans a day. (12) A group and a plan can be reported since 2026-11-21, with five reasons of their own, and whoever runs the server can look at a group, rename it, and remove a plan or the group (`group`, `rename-group`, `remove-plan`, `remove-group`; [running-a-server.md](running-a-server.md#groups)). The reasons and what the operator can do are built one way for now. The three apps offer the report. |
| Thermal forecast | **Open, five things**, each built one way for now ([design.md](design.md#thermals)). (1) The kinds of day have no colours of their own in the design pack: marks and the map use steps of the pack's `thermal` scale (weak 2, local 3, cross-country 5, big 6), and a day that is not flyable is a grey-violet veil on the map, because the pack's danger crimson is nearly the scale's darkest step. (5) Whether the estimate is checked against flown climbs, which the server could do from the flights it holds. |

## Risks

1. **Scope.** This is three mature products at once. The phase order is the mitigation.
2. **Empty community.** XContest has the network. The app must be the best logbook and cockpit with no friends on it, import history in bulk, and cross-post to XContest if XContest agrees. Since 2026-11-20 the iPhone app, and since the same day the Android app, hands a flight to XContest by the pilot's own upload and sends one to the DHV-XC through the interface it publishes ([data-sources.md](data-sources.md#leagues-a-flight-goes-to)); posting to XContest with one tap and fetching a pilot's history from it wait for XContest's answer to the owner.
3. **Lost tracks.** iOS background limits and Android battery managers kill trackers. One lost long flight loses a pilot for good.
4. **Data permissions.** Several sources that matter most at launch sites have no open licence: Holfuy wind stations, the DHV site database, airspace activation times, webcams.
5. **Liability.** Airspace data and assistant answers can be wrong. Everything is advisory, shows the age of its data and cites its source.
6. **Store review.** Background location and background audio need justifying; user content needs report, block and moderation. Since 2026-11-20 the server takes reports and its operator can take things down; the iPhone, the Android and the web app have the form for a report, and nothing blocks. A group's name and its members' plans can be reported since 2026-11-21 on the server and in the core; the three apps offer it.
